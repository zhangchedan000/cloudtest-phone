# 机型扩充计划：借鉴 dobox + 超越 dobox（2026-11-24 定，明天做）

## 为什么
机型库现在 80 款，但**跟板子显卡真匹配（Mali-G610）的只有 9 款**，其余 71 款是伪装档（高通 Adreno 等，只改了「文字层」，深度检测露馅、面板标风险）。用户要「机型变多又能放心用」。

反推 dobox 的结论（见 `魔云腾适配.md` 末两节）：
- **dobox 的非匹配机型也没魔法**——跟我们一样只改 OpenGL 文字层（改系统 `libGLESv1/v2/v3.so`：显卡名/版本/扩展/数值参数，glReadPixels 按序列号加扰动），**Vulkan / OpenCL / `/dev/mali0` / 性能 / 渲染一概没改**，照样露。
- dobox 敢上几十款非匹配机型的**真正底气是 Play Integrity（`pif.json`）**：每款配一台「过了谷歌认证的真机指纹」，让 App/谷歌的设备认证过关，跟底下是不是 Mali 无关。**这正是我们还没有的东西。**

现状核对（2026-11-24 代码里确认）：
- Play Integrity：**完全没做**，只被动设了锁 bootloader 的属性（service.go:816、check-tells.sh）。
- Vulkan：disguise.go 只换了 `vulkan.mali.so` 的文件名 + `ro.hardware.vulkan` 属性，**真正的 `VkPhysicalDevice` deviceName/vendorID/driverVersion 还是 Mali**（disguise.go:135-147 注释自己写了「显卡名还是 Mali，Vulkan 不伪装」）。
- GLES 文字层伪装：已有（`host/image/glshim/pp_glshim.c` → `libGLES_pp.so`，#150）。

**目标**：补上 dobox 的命门（Play Integrity），再把 dobox 没做的 Vulkan 也改了 → 71 款伪装档从「标风险」变「能放心用」，并比 dobox 扛得更深。

## 阶段 1：Play Integrity —— Tier A(BASIC) ✅ 完成并验证机制（2026-11-25）；Tier B(DEVICE/keybox) 不做
**做法与边界**（重要，见本文「⚠️ 阶段 1 的真正命门」「⚠️ 重大转折」两节）：
- **Tier A（BASIC，合规，已做）**：机型加 `playIntegrity` 标志（Pixel 等认证指纹）；指纹本身走现有 fingerprints/buildProps 系统（手机构建期就改好 build.prop，比 dobox 运行时改更干净）；开机后清一次 gms（照 dobox extservice2，让它用最终指纹重新评估，marker 防重复）。`catalog.go` 加字段、`settings.go` 加清 gms。
- **实测机制通过**（导入一个 Pixel `playIntegrity` 档、建 14-gms 机）：手机呈现成 **brand=google / model=Pixel 6a / 指纹 google/bluejay/bluejay:14/...release-keys**；清 gms 的 marker 已生成、gms 包+进程都在（没搞坏）、系统不崩。**实际过没过 BASIC 要装 Play Integrity 检测器 + 配套后端才能看（没搭）。**
- **怎么用**：用「兜底导入」导一份**当前有效的 Pixel 认证指纹**（PIF 社区维护、会轮换），或裸机型 JSON 里写 `"playIntegrity":true`；显卡建议按板子（Mali-G610，一致档，过认证靠指纹不靠显卡）。不内置固定 Pixel 档（指纹会过期、硬塞会误导）。
- **Tier B（DEVICE）不做**：扒实 dobox 的 keymint 是**软件的**（libpuresoftkeymasterdevice + 软件认证证书，不用 TEE）。软件要过 DEVICE 只能塞真机 keybox（盗用谷歌签名密钥、被持续吊销、绕过硬件认证），这条线不碰。

### （原计划）Play Integrity（pif.json）—— dobox 的命门，照着做
1. 原理：PIF——把一台「过了认证的真机」的 build 属性（BRAND/DEVICE/MODEL/FINGERPRINT/PRODUCT/MANUFACTURER/SECURITY_PATCH/`ro.build.version.*`/`ro.product.first_api_level`…）在开机时设进去，让 Play Integrity 的 **BASIC + DEVICE** 判定过（`MEETS_DEVICE_INTEGRITY`）。
2. 每款机型配一份 pif 档：优先用 dobox 包里的 `pif.json` / 我们真机采集的；没有就用一份「已知能过认证」的兜底指纹（PIF 社区维护）。
3. 注入点：管家开机本来就改 build 属性（`agent/internal/phones/buildprop.go`、`disguise.go`），把 pif 字段并进去。**关键看阶段 0 的发现**：没 root 框架时，光改 props 够不够让 gms 过；不够就要想办法 hook gms（dobox 怎么做的照搬）。
4. 范围说清：软件能过的是 BASIC + DEVICE；**STRONG（硬件级）要真 TEE 认证密钥，云手机普遍过不了**（dobox 有 `/dev/tee0` 真 TEE 也未必过 STRONG）。这板子有 TEE，到时看能走多远。
5. 验收：装个 Play Integrity 检测 App（或 pp-probe 加一项），重建前后对比判定等级。

**⚠️ 阶段 1 的真正命门（2026-11-25 查实）——DEVICE 判定要硬件 TEE**：
- Play Integrity 分三档：`MEETS_BASIC_INTEGRITY`（软件能过，靠指纹）、`MEETS_DEVICE_INTEGRITY`（**要硬件级 key attestation**，证书链到谷歌根，靠真 TEE）、`MEETS_STRONG_INTEGRITY`（更严）。**现在大多数风控要 DEVICE**。
- **板子有真 TEE**：宿主 `/dev/tee0`、`/dev/teepriv0` 都在。dobox 能过 DEVICE = 它①容器透传 `/dev/tee0`/`teepriv0` ②用 TEE 后端的 keymaster（RK3588 TEE 里有谷歌预置的认证密钥）③宿主跑 `tee-supplicant`（dobox 的 mytsvr 拉起）。
- **我们现状**：镜像用 `android.hardware.keymaster@4.1-service`（基本软件实现）、容器**没透传 tee0**、没跑 tee-supplicant → **只能过 BASIC，过不了 DEVICE**。
- **结论**：阶段 1「真正追平 dobox」= **TEE 硬件认证集成**（透传 tee0 + 换 TEE 后端 keymaster/keymint HAL + 接 RK3588 TEE 的 attestation 密钥 + 宿主 tee-supplicant），是 widevine 那种量级的工程，不是改 build.prop 那么简单。
  - **分两步走**：Tier A（先做、省）= build.prop 重写 pif 指纹 + `pm clear gms`，拿 BASIC（照 dobox 的 extservice2 做，我们构建期做更干净）；Tier B（大工程）= TEE 透传 + 硬件 keymaster，拿 DEVICE（真正追平 dobox）。
  - 验证卡点：Play Integrity 检测器 App（如 `1nikolas/play-integrity-checker-app`）还需配套云端项目解 token，github 无现成 release，要另找（F-Droid / 自建后端）；或用「硬件 key attestation」本地检测 App 直接看 attestation 是不是 TrustedEnvironment + 谷歌根。

**Tier A 具体做法（基于做实的 extservice2）**：
- 机型档加一个 `pif` 字段（或单独 pif 档）：存一台「过认证的 Pixel」指纹（BRAND/DEVICE/FINGERPRINT/MODEL/PRODUCT/SECURITY_PATCH/DEVICE_INITIAL_SDK_INT/...，格式照 `/mmc/data/*/modelData/pif.json`）。**跟显示机型分开**：显示还是小米/高通，认证指纹是 Pixel。先用 dobox 那份 Pixel 6a（bluejay）当通用兜底，够用再按社区 PIF 列表换新。
- 管家开机（`buildprop.go`/`disguise.go`/`phonecmd`）照 runload 做：① 设 `ro.build.version.security_patch` 等 Build 属性；② 把 pif 种进 gms（`/data/data/com.google.android.gms`，具体种什么等阶段 0 全量扒 runload 看穿）；③ 一次性标记（`.dobox_boot_seeded` 同理，种过不重种）。
- **先试最省的**：只设 Build 属性 + 种 gms，用 PI 检测 App 看能不能过 DEVICE 判定；过不了再上「gms 进程内改 android.os.Build 的 hook」（看 dobox 用框架覆盖包还是 native hook，照搬）。

## 阶段 2：✅ 完成并实测通过（2026-11-25）—— Vulkan 显卡名伪装（超越 dobox）
**实现**：`host/image/vkshim/pp_vkshim.c`（Vulkan 转接库，clang 无 NDK）挂成 `vulkan.<真机名>.so`，dlopen 真 Mali 驱动（HMI 其实在 libGLES_mali.so；真驱动挂隐藏点文件 `/vendor/lib64/hw/.vkreal.so`）做实际渲染，只拦 `vkGetPhysicalDeviceProperties(2)` 把 deviceName/vendorID 换真机的。`disguise.go` 的 `vkShimConfig` 写配置并挂 shim + .vkreal.so；`label.go` 给 .vkreal.so 打 same_process_hal_file；小助手删掉可见的 vulkan.mali.so 藏痕迹。deviceName 直接用 GL renderer（Adreno 一致）、vendorID 按厂商（Qualcomm=0x5143 等）。
**实测**（honor-bvl-an00，Adreno 750 伪装档）：`cmd gpu vkjson` 读出 **deviceName="Adreno (TM) 750"、vendorID=0x5143(Qualcomm)**（以前是 Mali）；/vendor/lib64/hw 只见 vulkan.adreno.so + 隐藏 .vkreal.so、不见 vulkan.mali.so；系统不崩。管家 4165479 已上板。**dobox 的 Vulkan 没伪装，这步超越了它。** 注：driverVersion 暂用真驱动的；真机精确 driverVersion 要真机采集（collect-model.py 后续可补，优先级低）。

### （原计划）Vulkan 显卡名伪装 —— 超越 dobox（它没做）
1. 做法：加一个 **Vulkan 层（VK_LAYER）或包一层 libvulkan**，拦 `vkGetPhysicalDeviceProperties(2)`，把 `deviceName`/`vendorID`/`deviceID`/`driverVersion` 换成机型的真机值。比直接改 `libGLES_mali` 干净，跟现有 GLES shim（pp_glshim.c）并列，新增 `pp_vklayer`。
2. 真机 Vulkan 值的来源：**今晚已确认 dobox 的 `device_info.json` 没有 Vulkan 字段（只有 gles20+egl）**，所以这步必须**先给 `host/models/collect-model.py` 加 Vulkan 采集**（真机上读 `VkPhysicalDeviceProperties`：deviceName/vendorID/deviceID/driverVersion/apiVersion），存进我们自己的机型档。dobox 导入的 71 款伪装档没有 Vulkan 数据，只能按 GPU 家族粗配或留 Mali（面板标）。→ 这也是「超越 dobox」的具体点：**我们采的机型比 dobox 多一层 Vulkan**。
3. 验收：装 Vulkan 信息 App，确认显卡名/厂商变成真机的。

### Tier B（TEE 硬件认证）可行性 + 路径（2026-11-25 探实）
**结论：硬件完全支持，确定可行（同款 Q1 硬件 dobox 已做到），是 widevine 量级的集成工程。**

探到的事实：
- 板子内核带 **OP-TEE**（dmesg `optee: probing for conduit method`）、`/dev/tee0`+`/dev/teepriv0` 在、宿主有 **`/usr/bin/tee-supplicant`**（没跑；dobox 的 mytsvr 会拉起）。
- dobox 的 `/vendor` 里有现成 **TEE 后端 KeyMint HAL**：`android.hardware.security.keymint-service.strongbox`、`keymint-service.vendor`、`android.hardware.gatekeeper@1.0-service.vendor`，+ 整套库（`android.hardware.security.keymint-V4-ndk.so`、`libkeymint.so`、`libsoft_attestation_cert.so` 等）。可像 widevine 那样从 dobox vendor 扒来移植。
- 我们现在用软件 `keymaster@4.1-service`、没透传 tee0、没跑 tee-supplicant。

实现路径（Tier B，按 widevine 的套路）：
1. **宿主**：开机起 `tee-supplicant`（OpenRC 服务；它替 TEE 做 RPMB / 文件等 supplicant 操作）。
2. **容器透传**：管家建容器时透传 `/dev/tee0`、`/dev/teepriv0`（像透传 mali0/mpp 那样，devclean 保留）。
3. **镜像**：从 dobox Q<ver> 扒 `keymint-service.vendor`（优先，不是 strongbox）+ 依赖库 + vintf 声明 + init.rc + selinux 规则，替换/叠加到我们镜像；去掉软件 keymaster@4.1 的声明，改用 TEE KeyMint。打标签、add-selinux 给二进制/库打对的域（hal_keymint 等）。
4. **验证**：① 容器里 keymint HAL 起来、连上 /dev/tee0；② 本地「硬件 key attestation」检测（KeyStore 生成带 attestation 的 key，看 securityLevel=TrustedEnvironment/StrongBox + 证书链到谷歌根）；③ 装 Play Integrity 检测器（配套后端）看 DEVICE 判定。
5. **坑预判**：RK3588 TEE 里要有谷歌预置的 attestation 密钥（出厂烧录）——dobox 能过说明 Q1 的 TEE 有；但我们的移植能不能让证书链正确上到谷歌根，是最大未知，要实测。keymint 版本要和安卓版本匹配（V3/V4）。RPMB、secure storage 可能要 tee-supplicant 配合。

**和 Tier A 的关系**：Tier A（build.prop pif + pm clear）单独只能过 BASIC；Tier B 到位才过 DEVICE。两者叠加 = 追平 dobox。

### ⚠️ 重大转折：dobox 的 keymint 是软件的，不是 TEE（2026-11-25 扒 keymint-service.vendor）
之前"Tier B = 透传真 TEE + 硬件 keymaster"的前提**错了**。实际扒 dobox 的 `keymint-service.vendor` 二进制：
- 链接 **`libpuresoftkeymasterdevice.so`（纯软件 keymaster）+ `libsoft_attestation_cert.so`（软件认证证书）**，源码 `device/myt/common/hals/Keymaster/keymint/service.cpp`。
- **没有** libteec、没有 `.ta`（Trusted App）、不连 `/dev/tee0`、vendor 里没有 optee_armtz 的 TA。
- → **dobox 的密钥认证完全是软件的，没用板子的硬件 TEE。** 我们现在的 `keymaster@4.1-service` 也是软件的，同一类。

**这对 Play Integrity DEVICE 判定意味着什么**：
- Play Integrity 的 DEVICE 判定要"证书链到谷歌根"的 key attestation。软件 keymaster 默认用的是 AOSP 公开的软件认证证书（securityLevel=Software，**链不到谷歌根 → 过不了 DEVICE，只能过 BASIC**）。
- dobox 要真能过 DEVICE，只有一种可能：`libsoft_attestation_cert.so` 里塞了一份**真实设备的「认证密钥盒 keybox」**（从某台真机抠出来的、能链到谷歌根的签名密钥）——即社区 TrickyStore/leaked-keybox 那套。这属于**盗用真机的认证签名密钥**，谷歌会持续吊销、且是绕过硬件级认证的安全机制。
- 也可能 dobox 其实只过 BASIC（我之前高估了它过 DEVICE）。

**结论 / 边界**：
- **能干净做的 = BASIC**（Tier A：build.prop 写一份 Pixel 认证指纹 + `pm clear gms`，和所有自定义 ROM 一样，合规）。
- **DEVICE 要 keybox**（盗用真机认证密钥、被谷歌当滥用持续吊销），这条线要用户明确决定，不默认做。
- 原"TEE 硬件集成"路子**不用做了**（dobox 都没走它）。
