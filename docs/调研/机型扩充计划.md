# 机型扩充计划：借鉴 dobox + 超越 dobox（2026-11-24 定，明天做）

## 为什么
机型库现在 80 款，但**跟板子显卡真匹配（Mali-G610）的只有 9 款**，其余 71 款是伪装档（高通 Adreno 等，只改了「文字层」，深度检测露馅、面板标风险）。用户要「机型变多又能放心用」。

反推 dobox 的结论（见 `魔云腾适配.md` 末两节）：
- **dobox 的非匹配机型也没魔法**——跟我们一样只改 OpenGL 文字层（改系统 `libGLESv1/v2/v3.so`：显卡名/版本/扩展/数值参数，glReadPixels 按序列号加扰动），**Vulkan / OpenCL / `/dev/mali0` / 性能 / 渲染一概没改**，照样露。
- dobox 敢上几十款非匹配机型的**真正底气是 Play Integrity（`pif.json`）**：每款配一台「过了谷歌认证的真机指纹」，让 App/谷歌的设备认证过关，跟底下是不是 Mali 无关。**这正是我们还没有的东西。**

现状核对（2026-11-24 代码里确认）：
- Play Integrity：**完全没做**，只被动设了锁 bootloader 的属性（service.go:816、check-tells.sh）。
- Vulkan：disguise.go 只换了 `vulkan.mali.so` 的文件名 + `ro.hardware.vulkan` 属性，**真正的 `VkPhysicalDevice` deviceName/vendorID/driverVersion 还是 Mali**（disguise.go:135-147 注释自己写了「显卡名还是 Mali，Vulkan 不伪装」）。
- GLES 文字层伪装：已有（`host/image/glshim/pp_glshim.c` → `libGLES_pp.so`，#150）。

**目标**：补上 dobox 的命门（Play Integrity），再把 dobox 没做的 Vulkan 也改了 → 71 款伪装档从「标风险」变「能放心用」，并比 dobox 扛得更深。

2. **消费者 = `runload`**（`/mmc/pp-build/dobox16-vendor/bin/runload`，14/15/16 都扒出来了）。它开机 init 阶段：播种机型数据、**碰 `/data/data/com.google.android.gms`**、设 `ro.build.version.security_patch`、用 `/data/system/.dobox_boot_seeded` 做一次性标记（种过就不重种）、链 `libjsoncpp` 解析 pif.json 等。→ **做法 = 开机把 pif 身份种进 gms 的 data + 设 Build 属性，一次性**。
3. **dobox 的 `device_info.json` 里显卡只有 `gpu.gles20.{vendor,renderer,version,extensions}` + `gpu.egl.*`，没有 Vulkan 字段** → 坐实它不伪装 Vulkan。我们做阶段 2（超越它）**得自己给 `collect-model.py` 加 Vulkan 采集**，dobox 数据里拿不到。
4. 现成资源都在板子：dobox 14/15/16 的 /system(bin+lib64) /vendor(bin/etc/lib64) 已扒（`/mmc/pp-build/dobox*-system|vendor`）；魔云腾两台旧实例完整 `modelData/`（含 pif.json、device_info.json、cpu/、telephone/camera/sensor/display/location/audio/input/features.json、hides.json、libc.so）在 `/mmc/data/*/modelData/`。lpunpack 在 `/mmc/pp-build/tools/`。

## 阶段 0：先拉 dobox，把它的做法做实（先做，半天）
**今晚已做掉大半（见上）。明天只剩一件硬的**：`runload` 开机碰了 gms data，但「pif 到底怎么只作用到 gms 认证进程（DroidGuard）、不让整机变 Pixel」还没完全看穿——**要全量扒 dobox 的 /system（现在只扒了 lib64+bin 的一部分）**，重点看：`runload` 往 `/data/data/com.google.android.gms` 种的是什么、有没有 `extservice2`（Java 系统扩展服务）或 `wuying_overlay_frameworks_base_core.apk`（框架覆盖包）在 gms 进程里改 `android.os.Build`。用 lpunpack 解 dobox super.img → debugfs rdump 全 /system。

只读静态分析，不动授权、不碰令牌/密钥。
1. 从 dobox 镜像的 **/system** 扒出改过的 GLES 库（之前只扒了 /vendor），和它注入 Play Integrity 的东西：
   - 它怎么注入 `pif.json`？哪个进程、什么路径、是不是社区 PlayIntegrityFix（PIF）那套字段？**重点：它没有 Xposed/Zygisk 框架是怎么让 gms/DroidGuard 吃到假指纹的**（改 build 属性够不够，还是 hook 了 gms 进程）。

2. 确认 dobox 的 `/system/lib64/libvulkan.so` 是**原版**（坐实「它 Vulkan 没伪装」），dobox 机型包 `device_info.json` 里**有没有 Vulkan 的 deviceName/vendorID/driverVersion**（阶段 2 要用；没有就得补采集）。
3. 结论写回 `魔云腾适配.md`。

## 阶段 1：Play Integrity（pif.json）—— dobox 的命门，照着做
1. 原理：PIF——把一台「过了认证的真机」的 build 属性（BRAND/DEVICE/MODEL/FINGERPRINT/PRODUCT/MANUFACTURER/SECURITY_PATCH/`ro.build.version.*`/`ro.product.first_api_level`…）在开机时设进去，让 Play Integrity 的 **BASIC + DEVICE** 判定过（`MEETS_DEVICE_INTEGRITY`）。
2. 每款机型配一份 pif 档：优先用 dobox 包里的 `pif.json` / 我们真机采集的；没有就用一份「已知能过认证」的兜底指纹（PIF 社区维护）。
3. 注入点：管家开机本来就改 build 属性（`agent/internal/phones/buildprop.go`、`disguise.go`），把 pif 字段并进去。**关键看阶段 0 的发现**：没 root 框架时，光改 props 够不够让 gms 过；不够就要想办法 hook gms（dobox 怎么做的照搬）。
4. 范围说清：软件能过的是 BASIC + DEVICE；**STRONG（硬件级）要真 TEE 认证密钥，云手机普遍过不了**（dobox 有 `/dev/tee0` 真 TEE 也未必过 STRONG）。这板子有 TEE，到时看能走多远。
5. 验收：装个 Play Integrity 检测 App（或 pp-probe 加一项），重建前后对比判定等级。

**明天具体做法（基于今晚做实的 runload）**：
- 机型档加一个 `pif` 字段（或单独 pif 档）：存一台「过认证的 Pixel」指纹（BRAND/DEVICE/FINGERPRINT/MODEL/PRODUCT/SECURITY_PATCH/DEVICE_INITIAL_SDK_INT/...，格式照 `/mmc/data/*/modelData/pif.json`）。**跟显示机型分开**：显示还是小米/高通，认证指纹是 Pixel。先用 dobox 那份 Pixel 6a（bluejay）当通用兜底，够用再按社区 PIF 列表换新。
- 管家开机（`buildprop.go`/`disguise.go`/`phonecmd`）照 runload 做：① 设 `ro.build.version.security_patch` 等 Build 属性；② 把 pif 种进 gms（`/data/data/com.google.android.gms`，具体种什么等阶段 0 全量扒 runload 看穿）；③ 一次性标记（`.dobox_boot_seeded` 同理，种过不重种）。
- **先试最省的**：只设 Build 属性 + 种 gms，用 PI 检测 App 看能不能过 DEVICE 判定；过不了再上「gms 进程内改 android.os.Build 的 hook」（看 dobox 用框架覆盖包还是 native hook，照搬）。

## 阶段 2：Vulkan 显卡名伪装 —— 超越 dobox（它没做）
1. 做法：加一个 **Vulkan 层（VK_LAYER）或包一层 libvulkan**，拦 `vkGetPhysicalDeviceProperties(2)`，把 `deviceName`/`vendorID`/`deviceID`/`driverVersion` 换成机型的真机值。比直接改 `libGLES_mali` 干净，跟现有 GLES shim（pp_glshim.c）并列，新增 `pp_vklayer`。
2. 真机 Vulkan 值的来源：**今晚已确认 dobox 的 `device_info.json` 没有 Vulkan 字段（只有 gles20+egl）**，所以这步必须**先给 `host/models/collect-model.py` 加 Vulkan 采集**（真机上读 `VkPhysicalDeviceProperties`：deviceName/vendorID/deviceID/driverVersion/apiVersion），存进我们自己的机型档。dobox 导入的 71 款伪装档没有 Vulkan 数据，只能按 GPU 家族粗配或留 Mali（面板标）。→ 这也是「超越 dobox」的具体点：**我们采的机型比 dobox 多一层 Vulkan**。
3. 验收：装 Vulkan 信息 App，确认显卡名/厂商变成真机的。

## 阶段 4：通用「兜底导入」机型参数（冗余）—— 用户要求
目的：方便随时换不同机型测。不管参数哪来的（dobox 包、别家、自己手搓、甚至不全），**导进来就能直接套用开机**，缺的字段自动拿板子的/默认值补上，面板如实标哪些没对上。

现状（2026-11-24 代码核对）：
- 已有导入 `ImportModels`（`agent/internal/phones/modelimport.go` + `import-model.py`）：**只认两种 zip**（我们采集的 / 魔云腾的），解析成 `Model` 档存进 `<数据目录>/models`、重载。
- `Model` 结构**绝大多数字段已是可选**（`omitempty`）：缺 CPUTree 用板子 cpu/、缺 ImeiTacs 随机、缺 Fingerprints 回退……都已有兜底 + 面板提示。**基础冗余已经在了**，缺的是「更宽的导入入口」。

要做：
1. **放宽导入格式**：除了现在两种 zip，再接受
   - 一份 `device_info.json`（dobox 单文件）或任意「参数 JSON」，字段能映射多少映射多少；
   - 一份 `build.prop` 转储 / 属性列表（只给 build 身份也能成一个最简机型）；
   - 直接贴 `Model` JSON（高级：手搓/改好的档直接存）。
2. **缺字段自动补齐**：导入时把没给的字段按板子实际值 + 通用默认填上（显卡→板子 Mali、CPU→板子 cpu/、特性→板子……），**保证"能开机、能用"**，不因为少几项就失败。
3. **面板如实标**：这台机型哪些是真机数据、哪些是兜底补的、哪些对不上（显卡/CPU/指令集），一眼能看出测试可信度。
4. **一键套用**：导入即出现在机型库，建手机直接选；（可选）支持「把某份参数直接套到已有的一台手机上」做快速对照测试。

验收：拿一份不完整的参数（比如只有 build 指纹 + 几个属性）导入 → 能建机、能开机、面板标出「兜底补齐」的项。

## 做不到的（跟 dobox 一样，先认了）
- 渲染结果、跑分、真实指令集：底下是 Mali/ARM，换不了（glReadPixels 扰动只能让每台不同，变不成 Adreno）。
- STRONG（硬件级）Play Integrity：要真认证密钥。
- 这些深度检测对「开发测试用途」影响多大，边做边看、面板如实标注。

## 顺序建议
阶段 0（拉 dobox 做实）→ 阶段 1（Play Integrity，命门，性价比最高）→ 阶段 2（Vulkan，超越 dobox）→ 阶段 3（多导入 + 定档）。每阶段自带验收，做完一阶段提交一次。
