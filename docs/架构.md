# 架构原则

改代码前先读这一页。本项目在自有或明确授权的私有测试环境中开发与验证，保留现有技术路线。架构和系统接口变更须说明实际机制、功能测试及回滚路径。

## 教训（来自 Prism 系统）

1. 先用别人的内核、后换官方内核 → 做了两遍。**前期把路线定死再做。**
2. 开发时依赖了 Win11 才有的东西，Win10 上缺一堆 → **不依赖开发机的特殊环境。**
3. 没写记录，改过的问题又重做 → **踩坑当场记，代码全进仓库，编译全用脚本。**

## 七条原则

1. **通用层和硬件层分开**
   - 通用层（换硬件直接复用）：`agent/`、`web/`、`profiles/` 的格式、`host/`。
   - 板级层（`boards/<板子>/`）：内核源码来源、显卡驱动版本、编译参数、安卓底子。
   - 换芯片 = 加一个 `boards/` 目录 + 一批匹配新显卡的机型档案，然后整体重测。
2. **每个机型可能不同的东西全写成配置（机型档案）**，不写死在代码里。档案格式带版本号。
3. **能放在我们自己代码里的，不依赖硬件或系统自带的**；只有显卡驱动这类真绑硬件的放板级层。
4. **不依赖开发机的特殊环境**：目标是通用 ARM64 Linux（Ubuntu/Debian），依赖写进 `host/` 安装脚本自动检查安装。
5. **依赖要写下来、查出来**：启动先做环境自检，缺什么明确提示怎么补。
6. **尽早在两种环境上跑**（甲骨文 + RK3588）。
7. **留扩展接口，不提前做功能**。

## 沿用 Prism 的规矩

- **一份定义，到处引用**：代理库、分组库、机型库各存一份，设备只存引用（`proxyId`、`groupId`、`modelId`）+ 手动改过的字段。
- 颜色只在一个地方定义（主题 tokens）。
- **代理缺失或不可用 → 禁止开机，绝不退回真实网络。**

## 结构

```
浏览器 / Prism ──HTTPS(登录)──> 管理页(web) ──接口+画面通道──> 管家程序(agent, 每台机器一个)
                                                                     │
                                                              安卓容器 × N
```

- 画面：安卓采集 → H.264 → agent → WebSocket → 浏览器 WebCodecs 解码。
- 操作：浏览器 → agent → 容器内 uinput 虚拟触摸屏/键盘（不用注入，不在安卓里装辅助 App）。
- 网络：宿主机 mihomo 透明代理，只作用于容器网段；宿主机自身（SSH、DC）不走代理。UDP/QUIC、IPv6、DNS 都要处理。

## 容器系统信息文件视图适配（甲骨文阶段不改内核）

| 接口或文件 | 当前实现 |
|---|---|
| `/proc/version`、osrelease、cpuinfo、midr_el1、CPU 频率 | 已有代码按机型档案生成替代内容，在容器开机后通过 bind mount 提供对应读取视图；并非修改宿主机内核 |

**原则**：区分“容器内文件视图调整”和“内核源码修改”；每一项明确代码、单测、实机验证状态。保留历史实现与测试记录，避免仅依据模块名称判断其功能。

## 开发和验证边界

- **容器与系统属性**：在专用测试容器中验证 Android 开机、属性读取、服务兼容性与异常恢复；使用自编测试程序及系统日志记录结果。
- **内核与板级驱动**：在专用 ARM 开发机或测试板进行源码构建、驱动兼容性和性能验证；高风险变更预置回滚方式，不能影响正常业务机器。
- **网络与远程控制**：使用隔离容器网段及授权出口进行连通性、DNS、IPv6、输入和画面测试；宿主机 SSH、管理通道和生产服务不受影响。
- **安全与准确性**：描述实际技术行为，不因术语调整而改变代码目的；涉及第三方身份识别、安全机制的具体请求单独评估，其他正常工程任务继续推进。

## 换板子 / 换宿主机的迁移清单（配置化原则，2026-11-19）

> **板子到了「从零跑起来」的完整上板流程见 `上板流程.md`**（刷机→binder 适配→Docker→Redroid→管家→风扇→GPU，已在魔云腾 Q1 RK3588 实战验证）。本节是其中**最后一步「防破绽」**的细节：默认板子已有「干净 Linux + docker + binder + 管家」底座。

**原则**：每台手机的身份尽量「自带、可移植」，不借用宿主机底层的值。换板子（新内核）时照这张清单走，不用重新摸索；大部分不变，真正要重做的只有内核模块重编一次。

**A. 已自成一套、换板子不变**（fakefs 按每台机型档案生成 → bind-mount 进容器，与宿主机无关）：
`/proc/cmdline`、`/proc/cpuinfo`、`/proc/version`、`osrelease`、kernel version、`boot_id`、各核 `midr_el1`、cpufreq。全来自机型档案。

**B. 动态读、不写死**：每台 `/data` 的来源盘（`/dev/sda1` / 磁盘镜像 `/dev/loopN` / 板子上可能是 `/dev/mmcblk*`）由管家开机时从这台手机**自己的挂载表**读出来登记给 pp_mnt（`mounts.go`），不写死宿主机的。

**C. 唯一跟宿主机内核绑的 —— 内核模块 pp_mnt / pp_uts（换板子必做）**：
因为 mountinfo（每进程）、uname（系统调用）、statfs（系统调用）、按 uid 的 `/proc/modules` 这些**没法用 bind-mount「自带文件」做**，只能挂内核函数。换板子步骤：
1. `bash host/build-kmod.sh pp_mnt pp_uts`（按板子内核头文件重编）；
2. 看 dmesg 有没有「没挂上 XX」——说明板子内核这个符号名不一样 / 被内联了，要找等价符号替换；
3. 依赖的内核符号：`do_statfs_native`/`do_statfs64`、`show_mountinfo`、`show_vfsmnt`、`show_vfsstat`、`tcp4/tcp6/udp4/udp6_seq_show`、`input_devices_seq_show`、`uptime_proc_show`、`modules_open`；
4. 模块里的值都是**算出来的 / 通用的**（uptime 用 `num_online_cpus()`、statfs 用通用 ~6GB、设备号用 dm-0/dm-34），不是宿主机的，所以**重编即可、不用改值**；
5. 重编加载后 `bash host/check-tells.sh <手机ID>` 复验。加载走「防失联」流程（编临时→insmod新不覆盖旧→验证→持久化）。

**D. 板子天生就对、仅这台 VM 需要的权宜之计（换板子自然消失 / 可去掉）**：
SELinux（板子 Enforcing → `/proc/modules` 天生拒 App，内核那条 EACCES 可留可去）、QEMU/virtio 设备、软件 GPU（SwiftShader）、CPU 只有 4 核无频率、`/sys/module` 里的 xen/kvm/virtio/vmw。

**E. 不得不借宿主机、但必须借的**：fakefs 的 `/proc/cpuinfo` 的「Features 能力字段」照抄宿主机——不能谎称 CPU 没有的能力，否则 App 调用会崩。板子是真 ARM SoC，比这台服务器 CPU 更接近目标机型，天生更准。

**今后加新改动的取舍**：能用「自带文件（fakefs bind-mount）/ 改镜像 / 改档案」干净做到的，就那样做（可移植、不依赖宿主机内核）；只有做不到时（每进程文件、系统调用、按 uid 行为）才用内核模块，并保持 best-effort（挂不上只记日志、不影响开机）。
