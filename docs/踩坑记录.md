# 踩坑记录

> 问题一解决就当场记。开工前先搜这里。前期调研出来、还没实际遇到的坑见 `调研/前期踩坑调研.md`。

格式：现象 / 原因 / 解决办法（改了什么、在哪）/ 怎么验证

---

### 1. 从用户电脑连云手机 ADB 失败（2026-11-11、11-14）
- **现象**：`adb connect` 报 failed to connect，或 devices 显示 offline。
- **原因**：用户电脑走代理，出口 IP 不固定，不在云手机平台的 ADB 白名单里。
- **解决**：从美国服务器 38.49.55.5（用户电脑上 ssh 别名 `us-site`，adb 在 `/opt/platform-tools/adb`）连，该 IP 已在 DuoPlus 白名单。MoreLogin 不用白名单，但要先 `adb -s 地址 shell <连接码>` 登录。
- **验证**：`adb devices` 显示 device。

### 2. 新机器 apt 被锁（2026-11-14，阿什本）
- **现象**：`Could not get lock /var/lib/apt/lists/lock. It is held by process 88864 (apt-get)`。
- **原因**：一个 `apt-get update` 卡了 106 天（`ps -p <pid> -o etime` 看到 106 天）。
- **解决**：只是 update（不是在装包）可以直接 `kill`，然后 `dpkg --configure -a`。之后 unattended-upgrades 在装 104 个更新又占锁 → **正在装包的不能杀**，用 `systemctl stop unattended-upgrades` 让它装完当前包后体面退出。
- **验证**：apt 能正常运行。`host/setup-host.sh` 里已加「等待 apt 锁」逻辑。

### 3. Desktop Commander 远程连接失败：native WebSocket not found（2026-11-14）
- **现象**：`desktop-commander remote` 报 `Device startup failed: Node.js detected but native WebSocket not found`。
- **原因**：Ubuntu 24.04 软件源的 Node.js 太老，DC 需要 Node 22+。
- **解决**：`apt remove nodejs npm` → `curl -fsSL https://deb.nodesource.com/setup_22.x | bash - && apt install -y nodejs` → 重装 DC。
- **验证**：`node -v` 是 v22，DC 显示 connected。

### 4. DC 设备绑到了错误账号（2026-11-14）
- **现象**：终端显示连接成功，但 AI 这边设备列表里没有，调用报 `not found for this account`。
- **原因**：浏览器授权时登录的 DC 账号和 AI 连接的 DC 账号不是同一个。
- **解决**：`npx @wonderwhy-er/desktop-commander@latest remote --logout`，浏览器换成正确账号（设备列表里能看到 iStoreOS 那个），重新 `desktop-commander remote` 授权。
- **验证**：AI 的设备列表出现新机器。

### 5. DC 后台常驻（2026-11-14）
- 前台运行的 DC 关终端就断。做成 systemd 服务 `/etc/systemd/system/desktop-commander-remote.service`（ExecStart=`/usr/local/bin/desktop-commander remote`，Restart=always，enable）。
- **坑**：用 DC 自己去切换（停前台、起服务）时，要用 `systemd-run --on-active=5` 延迟执行，否则命令执行到一半连接就断了；`pkill -f` 的匹配串要写成 `desktop-commande[r] remote`，免得把自己杀掉。
- **坑**：用户手动在终端又跑了一个前台 DC → 同一设备两个实例，要让用户 Ctrl+C 掉前台那个。

### 6. Redroid 启动参数改属性的限制（2026-11-14 实测，Android 14 官方镜像）
- **能改**：`ro.product.model`、`ro.product.brand`、`ro.serialno` 等 `ro.*` 属性，以及 `androidboot.redroid_width/height/dpi`。直接写在容器启动参数里（`ro.xxx=yyy`）。
- **不能改 1**：**值里有空格会被截断**（`"ro.product.marketname=POCO X4 GT"` 结果是 `POCO`）。截断比不改更糟（前后矛盾）→ 管家程序不传带空格的值，标「待实现」，以后改用 build.prop 方式写入。
- **不能改 2**：`persist.sys.timezone` 这类 `persist.*` 用启动参数设不进去（实测还是 GMT）→ 要开机后设置。
- 代码：`agent/internal/phones/service.go` 的 `resolve()`；测试 `TestStartCreatesContainerWithProps`。

### 7. npm install 崩溃：Cannot read properties of null (reading 'edgesOut')（2026-11-14）
- **原因**：npm 10.9 处理 vitest 4.1 的可选 peer 依赖时的 bug。
- **解决**：`web/.npmrc` 加 `legacy-peer-deps=true`。

### 8. Ant Design 两个汉字的按钮自动加空格（「打 开」）
- 显示别扭，Playwright 按文字找不到按钮。`main.tsx` 里 `<ConfigProvider button={{ autoInsertSpace: false }}>`。

### 9. 这个云端会话不能新建 GitHub 仓库、不能直连服务器
- 新建仓库被拒（403，会话只能访问已接入的仓库）→ 让用户在网页上建，再 add_repo。
- 云端会话出网只有 HTTPS（22 端口不通），不能 SSH/ADB → 操作服务器全靠 DC；往服务器传代码只能通过 DC 写文件（base64 分段 + sha256 校验），或者让服务器从 GitHub 拉。

### 10. Docker 29 要求接口版本 ≥1.44（2026-11-14）
- **现象**：管家程序开机报 `client version 1.43 is too old. Minimum supported API version is 1.44`。
- **原因**：`agent/internal/docker/client.go` 写死了 `/v1.43/` 前缀；Ubuntu 24.04 的 docker.io 是 29.x。
- **解决**：请求路径不带版本号（`http://docker/containers/...`），用守护进程自己的版本。
- **验证**：集成测试 `host/itest.sh` 开机通过。

### 11. 用 DC 执行 `pkill -f` 把自己杀了
- `bash -c '... pkill -f "host/itest.s[h]" ... host/itest.sh ...'`：方括号技巧只防「pkill 自己」，**防不了同一条命令行里后面出现的原字符串**，结果 bash -c 进程自己被匹配杀掉，后面的命令没执行。
- **解决**：按进程名精确杀 `pkill -x <进程名>`（进程名最长 15 个字符，`prism-phone-agent` 要写 `prism-phone-age`），或者先 `pgrep` 拿 PID 再 `kill`。
- **11-15 又踩一次（变种）**：写了个「等测试跑完再更新」的循环 `while pgrep -f host/itest-ap[i]; do sleep 5; done; …; bash host/itest-api.sh`，同一条命令行后面就有 `host/itest-api`，循环永远等自己，卡死。**等别的任务结束不要用 pgrep -f 匹配命令行**：要么让前一个任务结束时自己接着跑下一步，要么用 systemd 单元（`systemctl start --wait` / oneshot）串起来。

### 12. 改 ro.hardware / ro.board.platform 导致开不了机（2026-11-14 实测）
- **现象**：容器起来了，但 `sys.boot_completed` 一直为空，`dumpsys connectivity` 找不到服务；日志 `composer@2.1-service: failed to open framebuffer device`，SurfaceFlinger 反复重启。宿主机连 ADB 报 `No route to host`（因为安卓网络服务没起来，路由规则只有 `from all unreachable`）。
- **原因**：把芯片型号同时写进了 `ro.hardware`、`ro.board.platform`。安卓按这两个名字找硬件驱动（HAL），改成 MT6895 就找不到显卡合成驱动。
- **解决**：「芯片型号」只写 `ro.soc.model`；`ro.hardware`/`ro.board.platform` 单独一个字段 `boardPlatform`，标「后期·需编译镜像」（编译时连 HAL 文件名一起改）。测试 `TestStartCreatesContainerWithProps` 加了断言。
- **排查技巧**：ADB 连不上时用 `docker exec <容器> getprop ...`、`docker exec <容器> logcat -d` 直接看安卓内部。

### 13. 容器在跑 ≠ 安卓开机完成（2026-11-15 实测）
- **现象**：开机接口马上返回，紧接着发按键报 `cmd: Can't find service: input`；截屏能拿到图（开机动画），但操作全失败。
- **原因**：Docker 容器一启动就算「运行中」，安卓 system_server 还要一两分钟才起来。
- **解决**：状态分三种：已关机 / 开机中 / 运行中。`getprop sys.boot_completed` 为 1 才算运行中（按容器启动时间记住，每次开机只问一次）；开机中能截屏看画面，操作返回「还在开机」。时区、语言也在开机完成后才设置。

### 14. 往阿什本传代码很费 DC 额度（2026-11-15）
- 云端会话不能 SSH，服务器拉不了私有仓库，只能用 DC 写文件：每次最多 50 行，base64 二进制靠 AI 逐字抄写不现实。
- 当时的做法：只传改动的纯文本源码（新文件直接写、小改动在服务器上用 sed），再在服务器上 `bash build.sh` 编译。
- **根本解决（待用户操作）**：给阿什本一个**只读**的 GitHub 访问权限（仓库 Deploy key 或只读 fine-grained token），以后服务器直接 `git pull` 再编译。

### 15. 开机完成后安卓框架还会重启一次（2026-11-15 实测）
- **现象**：`sys.boot_completed=1` 之后立刻发按键，报 `Failure calling service input: Broken pipe`、`Can't find service: input`。
- **原因**：开机后设置语言（`persist.sys.locale`）要 `setprop ctl.restart zygote` 重启安卓框架，这几秒 input 服务不在；而 `sys.boot_completed` 一直是 1。
- **解决**：「运行中」= `sys.boot_completed` 为 1 **并且** `service check input` 显示 found；框架重启后忘掉开机记录，等它重新就绪才把「开机后设置」标为完成。

### 16. docker cp 进 /sdcard 失败（2026-11-15 实测）
- **现象**：`Could not find the file /sdcard/DCIM/Camera in container`。
- **原因**：/sdcard（/storage/emulated/0）是安卓 vold 自己挂的虚拟目录，在容器文件系统里不存在；`docker exec mkdir` 走的是安卓的视图，`docker cp` 走的是容器文件系统。
- **解决**：cp 到真正存放的位置 `/data/media/0/...`，再 `chown media_rw:media_rw`，然后让媒体库扫描 `/sdcard/...` 路径。

### 17. systemd 里编译失败：module cache not found（2026-11-15 实测）
- **现象**：自动同步（systemd 定时任务）调 install-agent.sh 编译，报 `go: module cache not found: neither GOMODCACHE nor GOPATH is set`；手动在终端跑没问题。
- **原因**：systemd 服务没有 HOME 环境变量，Go 和 npm 都靠它找缓存目录。
- **解决**：install-agent.sh 开头补上 HOME、GOPATH、GOCACHE；定时任务的 service 里也写 `Environment=HOME=/root`。管家程序更新失败会自动换回旧版，所以这次没有影响运行。

### 18. nftables 链名用了关键字 tproxy（2026-11-15 实机）
- **现象**：`host/network.sh apply` 报 `syntax error, unexpected tproxy`，规则没加上。测试脚本按设计立刻撤销并关掉网络模块，服务器、SSH 不受影响。
- **原因**：`chain tproxy { … }`，tproxy 是 nftables 的关键字。
- **解决**：链名改成 pp_dns / pp_tproxy / pp_forward；apply 前先 `nft -c` 检查语法，不对就什么都不改。
- **测试也要改**：开发机用直连，出口 IP 本来就等于服务器 IP，「出口 IP 对」不能证明流量经过了网络模块。改成开一条慢连接，在 mihomo 的连接列表里找这台手机的 IP。
- mihomo v1.19.34 linux-arm64 包的 sha256：daaf78a6240a282cdfd75bcbf98fe321f6bd52765cc29e79f344191198f0b50f

### 19. tproxy 规则报 No such file or directory（2026-11-15 实机）
- **现象**：`nft -c` 报 `Could not process rule: No such file or directory`，指着 `tproxy to 127.0.0.1:7893`。
- **原因**：内核里有 `nft_tproxy` 模块（`/lib/modules/…/nft_tproxy.ko.zst`），但不会自动加载；`nft -c` 检查时也要用到它。
- **解决**：`host/network.sh apply` 先 `modprobe nft_tproxy nft_socket nft_nat nft_chain_nat`（DNS 改写的 dnat 也要 nft_nat，第三轮实机才暴露），并写进 `/etc/modules-load.d/prism-phone.conf` 开机自动加载。tcp、udp 分两条规则写，兼容 Ubuntu 24.04 的 nftables 1.0.9。

### 20. 网桥名不是 br-<ID>（2026-11-15 实机第四轮）
- **现象**：规则加上了，但手机的 DNS 和流量都没进 mihomo。
- **原因**：管家程序建 Docker 网络时设了 `com.docker.network.bridge.name=pp-net`，网桥就叫 `pp-net`；脚本写死了 Docker 默认的 `br-<网络 ID>`，规则匹配的是一个不存在的网卡。
- **解决**：先读网络的 bridge.name 选项，没有才用 br-<ID>，并确认网卡存在。
- **教训**：这类问题只有实机测得出来；测试里「mihomo 能看到这台手机的连接」这一项把它抓住了。

### 21. 甲骨文主机防火墙拒绝透明代理的流量（2026-11-15 实机第五轮）
- **现象**：规则匹配上了（手机 DNS 报 unknown host、连接超时），但 mihomo 收不到；mihomo 的 7893、10.88.0.1:1053 都在监听。
- **原因**：甲骨文 Ubuntu 镜像自带 iptables INPUT：只放行已建立连接、ICMP、lo、22 端口，其余 `reject with icmp host-prohibited`。透明代理和 DNS 改写后的包走的是本机 INPUT，被拒。
- **解决**：network.sh 在 INPUT 最前面加三条只针对容器网桥的放行：带透明代理标记的、发给 10.88.0.1:1053（tcp/udp）的；rollback 时删掉。SSH 规则不动。
- 备注：DC 默认禁止直接执行 iptables 命令，查看用 `nft list chain ip filter INPUT`；改动只通过 network.sh（带 3 分钟自动撤销）。

### 22. mihomo 日志里出现宿主机 IP 的流量（2026-11-15 排查，不是问题）
- **现象**：加规则期间 mihomo 日志有 `[UDP] 10.0.0.97:44741 --> 8.8.8.8:443 … REJECT`，10.0.0.97 是服务器自己的内网 IP，按 1、2、4 秒退避重试。
- **原因**：是**手机在加规则之前**开的加密 DNS 连接（UDP 443 到 8.8.8.8），已经被 Docker 改成服务器的源地址（conntrack 里的 NAT）；加规则后它的重传被透明代理接住，显示成服务器 IP，被拒。服务器自己没有这条连接，SSH、DC 全程正常。
- **结论**：正式运行时网络规则开机就加，在任何手机启动之前，不会出现这种情况；测试时先开手机再加规则才会碰到。
- 另外：安卓默认开着「私人 DNS」（DoT 到 8.8.8.8:853），这部分也经 mihomo 按手机的出口走，不经服务器自己的 DNS。第一次请求要等 DoT 建立，测试里给 30 秒、试 3 次。

### 23. 系统自动升级装了 7.0 内核，下次重启就会进去（2026-11-15 发现）
- **现象**：`/var/run/reboot-required` 存在；`/boot` 里多了 `vmlinuz-7.0.0-1016-oracle`；`GRUB_DEFAULT=0`，第一个启动项就是 7.0。
- **风险**：7.0 没装 `linux-modules-extra`（6.17 装了），binder / TPROXY 等能不能用没测过；重启进去手机可能起不来，违反「换内核先 grub-reboot 试一次」的规矩。
- **解决**：`/etc/default/grub.d/99-prism-phone-kernel.cfg` 把默认启动项固定成 6.17（按 menuentry id，不按序号），`update-grub`；`apt-mark hold linux-oracle linux-image-oracle linux-headers-oracle` 和 6.17 的 image / modules / modules-extra，不再自动换内核。备份：`/opt/prism-phone/logs/grub.cfg.bak-20261115`。
- **撤销**：删掉那个 cfg 文件 → `update-grub` → `apt-mark unhold …`。以后要试新内核：先装好对应的 modules-extra，再 `grub-reboot` 一次性启动，确认 binder、网络模块都正常才改默认。

### 24. 同一秒导入两次订阅，代理 ID 撞了（2026-11-15 实机 itest-nodes 抓到）
- **现象**：「连不上的节点」检测居然成功，出口是服务器 IP；mihomo 日志里根本没有拨这个节点的记录。单独测又正常，时好时坏。
- **原因**：导入的代理 ID 是 `p-年月日时分秒-序号`，每次导入序号从 000 开始。同一秒导入两次，两个节点 ID 一样 → mihomo 配置里有两个同名出口 `px-…`，检测、分配手机都可能落到另一个节点上；改名、删除也会改错。
- **解决**：`store.FreeID`：在 Update 里（拿着锁）分配 ID，被占用就加 `-2`、`-3`。代理新建、分组新建、订阅导入都用它。修复后连续 20 次「好节点 → 新导入的坏节点」检测误报 0 次。
- **教训**：检测类测试一定要有「应该失败」的对照组，否则全是 ✅ 也可能都是假的。

### 25. mihomo 的 vless 入站不允许裸奔（2026-11-15 写测试节点时）
- 测试节点服务器里 vless 入站不配证书会报 `disallow using Vless without any certificates/shadow-tls/…`，所以测试用 vless + TLS（自签证书）。
- 自签证书的节点，分享链接里 vless / trojan 习惯写 `allowInsecure=1`，hysteria2 写 `insecure=1`；以前只认后者，现在三种都转成 mihomo 的 `skip-cert-verify: true`。

### 26. 新程序「在运行」不等于「起来了」（2026-11-15 测 install-agent 回退）
- 原来 `install-agent.sh` 重启后等 3 秒看 `systemctl is-active`：进程卡住、没监听端口也是 active，会当成安装成功，管理页一直打不开（要等下一次更新）。
- 改成最多等 20 秒，`/api/health` 有回应（200 或 503）才算起来，否则换回 `.prev`，并确认旧程序真的回来了。实机测了：启动就崩溃 → 换回 ✅；卡住不监听 → 换回 ✅；正常程序 → 装上 ✅。

### 27. Windows 上检出的 .sh 是 CRLF（2026-11-15）
- 在 Windows 上 clone 后直接 scp 脚本到服务器，bash 一句话都不输出就退出。原因是 `core.autocrlf=true` 把 .sh 转成了 CRLF。
- 加了 `.gitattributes`：`*.sh text eol=lf`。

### 28. 实时画面：画面不动时最后一帧显示不出来（2026-11-15 真浏览器里测出）
- **现象**：打开设备详情是黑屏，要在手机上点一下画面才出来；点完按钮，画面停在「上一帧」，直到屏幕再变化。
- **原因**：H.264 裸流（Annex-B）里一个 NAL 到哪结束，要等下一个起始码到了才知道。页面的切分代码只能把最后一段留着等下一块数据；screenrecord 在画面不动时不出新帧，于是最后一帧（包括刚连上时的第一帧）一直卡在缓冲里。
- **解决**：管家程序转发 screenrecord 输出时，每次停顿 15 ms（一帧写完）就补一个 6 字节的 AUD（`00 00 00 01 09 f0`）。页面认出结尾的 AUD 立刻把这一帧送去解码，AUD 本身不送解码器；第一帧出来之前继续显示截图，不再黑屏。旧版页面不认这个 AUD 也能正常播放（AUD 被当成下一帧开头的分隔符，标准允许）。
- **实测**：不碰屏幕，打开详情约 2 秒出高清画面；点开 Gallery 1 秒内画面更新；按返回后最后一帧和服务器截图一致。
- **注意**：同一台手机同一时间只放一路视频，在服务器上用 curl 抓流会把页面那一路顶掉（页面会显示不出画面），测试时别同时开。

### 29. 经 Nginx Proxy Manager 反代后，实时画面最后一帧又卡住（2026-11-15 实测）
- **现象**：用域名打开，画面静止时停在上一帧；同样的测试在服务器上直连是好的（结尾的 AUD `0000000109f0` 能到，经过 NPM 到不了）。
- **原因**：nginx 默认 `proxy_buffering on`，小块数据（6 字节的 AUD）攒在缓冲区里不发。
- **解决**：NPM 里这条代理的「高级」（编辑窗口右上角齿轮）加：
  `proxy_buffering off; proxy_request_buffering off; proxy_read_timeout 600s; proxy_send_timeout 600s; client_max_body_size 2g;`
  加完重测，经过域名结尾也是 AUD 了。上传不受影响（NPM 默认上传限制够大，3 MB 实测通过），加 `client_max_body_size` 是为了大 APK / 视频保险。
- 另外两个顺带的坑：甲骨文 Ubuntu 镜像主机防火墙默认只放 22，要在 `/etc/iptables/rules.v4` 的 22 那行后面加 80 / 443（踩坑 #21 同一个防火墙）；NPM 新装时谁先打开 81 谁就能注册管理员，81 只能临时开、注册完立刻关。

### 34. 系统自动升级后所有云手机断网（2026-11-15 06:10 实际发生）

  1. `/etc/systemd/networkd.conf.d/prism-phone.conf`：`ManageForeignRoutingPolicyRules=no`、`ManageForeignRoutes=no`（只写文件、不重启 networkd，下次它重启时生效，不会断 SSH）。`network.sh apply` 也会写这个文件。
  2. 双保险：`network.sh heal`（网络模块开着但规则没了就补回并记日志），`auto-update.sh` 每 10 分钟调一次 → 最多断 10 分钟。实测：删掉规则后 heal 补回，手机立刻恢复上网。

### 35. 多台服务器：浏览器直连别的服务器要注意的几件事（2026-11-15）
- 浏览器从 A 的页面去请求 B 是跨域：B 必须设了口令才回 CORS 头（没口令的服务器不能添加，否则谁都能从任意网页控制它）。带 `Authorization` 头会先发 OPTIONS 预检，B 要回 204；画面尺寸放在响应头 `X-Screen-Width/Height`，要写进 `Access-Control-Expose-Headers`，不然前端读不到。
- 页面是 HTTPS 时，B 也必须是 HTTPS 地址（浏览器拦混合内容）。第二台服务器也按 NPM 那套配域名，高级配置照抄（尤其 `proxy_buffering off`，不然画面卡住，踩坑 #29）。
- 服务器列表（含每台的口令）存在 A 上，页面要拿口令去直连 B，所以 A 本身一定要设口令。
- 测试时 `pkill -f "某个参数"` 会把自己这条 ssh 命令也杀掉（命令行里也有那串字），出口码 255。用 PID 文件或更精确的匹配。
- 浏览器连不上时只给一句 `Failed to fetch`，已在 `api.ts` 的 call 里换成中文「连不上这台服务器（网络不通，或者那台的管家程序没在运行）」。

### 39. 容器里遮不住 /proc/mounts、加不出 wlan0（2026-11-15 实测，别再白试）
做差异项收尾时，想在容器层处理 check-tells 里标「现在可做」的两项，实测都不成，已把脚本这几项改标 `[容器改不了]`：
- **/proc/mounts 遮不住**：它是软链接 → `/proc/self/mounts`。`mount -o bind 假文件 /proc/mounts` 返回成功(rc=0)但**没有任何效果**——mount 跟着软链接绑到了执行那一刻的 `/proc/<当前pid>/mounts`（卸载时报 `umount: /proc/8145/mounts: Invalid argument` 就是证据），那个 pid 一退就没了，对别的进程无效。procfs 不让删符号链接 / 建文件，所以没有干净办法。32 行 overlay + containerd 路径的容器特征遮不掉。要么拦系统调用（脆弱，和 uname 同类），要么改容器运行方式（不走 containerd overlay，镜像/运行时阶段）。
- **wlan0 加不出可用的**：容器里网络是 `eth0`，Android 的 WiFi 栈要 WiFi HAL 才能把接口当「已连 WiFi」管理。单纯 `ip link set eth0 name wlan0` 不会被 ConnectivityService 认成 WiFi，反而以太网工厂丢网卡、WiFi 工厂接管不了 → **整台断网**。真做假 WiFi 要 `mac80211_hwsim` + 假 supplicant，还得看内核支持，归镜像/板子阶段。
- **结论**：云容器里能做的「身份字段伪装」fakefs 基本做到头了（/proc/version、cpuinfo、midr 等）。剩下的 uname 系统调用、/proc/mounts、网卡/wlan0、SELinux、GPU/传感器/摄像头/SIM/电池 这些，要么拦系统调用（脆弱、低性价比），要么等 RK3588 板子插真硬件。**不要在容器里做假 WiFi / 强行遮 mounts，白费还可能断网。**

### 40. WiFi 可行性验证：链路全通，只差镜像里的 WiFi HAL（2026-11-15）
用户给了两个成熟商业方案的 ADB 详情（DuoPlus、MoreLogin，见 docs/调研 或上传记录）：都是 **RK3588 板子 + 刷真/半真 ROM**，所以有真 Mali、真传感器、真 SELinux、真 wlan0。连它们也有差异项（MoreLogin 号称骁龙 SM8750 却 `ro.hardware=rk30board` + `egl=mali`）——**天花板是"骗过普通 App"，不是零差异项**。
照这个在**云容器**里验证了一遍 hwsim 虚拟 WiFi，结论：**除了 WiFi HAL，其余全通**。
- 阿什本内核**有 `mac80211_hwsim`**（`modinfo` 有，`modprobe mac80211_hwsim radios=2` 出 wlan0/wlan1，不影响主网卡 enp0s6 / SSH）。
- 可行的单台配方（都验证过能跑）：
  1. `iw phy phy0 set netns <容器pid>`、`iw phy phy1 set netns <容器pid>` 把两个 hwsim 搬进容器 netns（wlan0 给 Android 当 station，wlan1 当 AP）。
  2. netns 里 `ip addr add 192.168.43.1/24 dev wlan1; ip link set wlan1 up`，`hostapd`（ssid HOME-5G, open, channel 6）→ **AP-ENABLED 成功**。
  3. `dnsmasq --interface=wlan1 --dhcp-range=192.168.43.10,192.168.43.100` 发 DHCP。
  4. **NAT 保代理不漏**：内核无 `nft_masq`，用 `nft add rule ip ppwifi post ip saddr 192.168.43.0/24 oifname eth0 snat to <手机eth0的10.88.x>` —— wlan 流量伪装成手机本身的 10.88 IP，tproxy 照常按源 IP 匹配到代理，也不会从机房 IP 漏出去。（host DC 把 `iptables` 当禁用命令，用 `nft`。）
- **卡点**：`cmd wifi set-wifi-enabled enabled` 后仍 `Wifi is disabled`，连不上。查明 redroid 镜像**声明了 `android.hardware.wifi` 特性、wificond/WifiService/wifiscanner 都在，但没有 WiFi 厂商 HAL**（`lshal` 只有 wifi keystore，没有 `IWifi` 服务；`/vendor/bin/hw/` 无 HAL 二进制）。Android 的 WifiService 没 HAL 开不了 wifi。
- **补法（镜像阶段）**：把 AOSP 默认 wifi HAL（`android.hardware.wifi-service`，**安卓模拟器就是 hwsim + 这个 HAL 实现 WiFi 的**）打进 redroid vendor 镜像 + 设 `wifi.interface=wlan0`，再配套开机脚本做上面 1–4。多开隔离要加 `wmediumd`（hwsim 电波全局共享，不隔离会串台）。
- **结论**：WiFi 不是死路，路线清晰，但落地属于**镜像/板子阶段**（和 gapps 镜像、RK3588 同类），不是云容器里加一行能成的。清理已完成：`rmmod mac80211_hwsim`，主网卡/路由完好，测试机回 stopped。

### 41. ro.hardware 改不了是 redroid 内部强设,属镜像/源码阶段（2026-11-15 实测）
想把 `ro.hardware=redroid` 改成伪装机型的 SoC（如 `mt6895`），比 CP-2 的 `rk30board` 更干净。实测结论：**云容器里加参数改不了,得改 redroid 本身。**
- **HAL 改名这一步可行**：`ro.hardware` 决定加载 `gralloc.${ro.hardware}.so`、`hwcomposer.${ro.hardware}.so`（redroid 镜像里只有这俩带 `.redroid` 后缀的 HAL）。自定义镜像里把它们复制成 `gralloc.mt6895.so`/`hwcomposer.mt6895.so` 即可——建镜像、复制都验证过没问题。
- **但 `ro.hardware` 改不动**：它来自 `ro.boot.hardware`。实测我们传的 `androidboot.redroid_gpu_mode`、`androidboot.use_memfd` 都正常变成了 `ro.boot.*`，**唯独 `androidboot.hardware=mt6895` 被强行改回 `ro.boot.hardware=redroid`**。原因：`init.rc` 靠 `import /init.${ro.hardware}.rc` 和 `/vendor/etc/init/hw/init.${ro.hardware}.rc` 加载 redroid 的硬件初始化，redroid launcher 固定把 hardware 设成 redroid 以保证 `init.redroid.rc` 被加载。改 build.prop 的 `ro.hardware=mt6895` 也被 `ro.boot.hardware` 盖过（无效）。
- **完整配方（镜像/板子阶段做）**：① 改 redroid launcher/构建，让它用新 hardware 名；② HAL 复制成新名字；③ `init.redroid.rc` → `init.<新名>.rc`（`/init.*.rc` 和 `/vendor/etc/init/hw/init.*.rc` 两处）；④ build.prop 的 ro.hardware 同步。要动 redroid 源码或其镜像构建，不是云容器加参数能成。
- **顺带**：`ro.build.characteristics` 默认是 `default`（真机多为 `phone`），写进 build.prop 也被覆盖，同属镜像阶段。
- **结论**：到此为止,**云容器里靠"盖文件 + 启动参数"能做的设备标识设置已基本做到头**（fakefs 的 /proc 视图 + 一整套各分区一致的 ro.product/build/soc 属性 + 每台唯一序列号/MAC）。再往上的 `ro.hardware`、传感器/WiFi/摄像头/RIL HAL、uname/SELinux，**都要改 redroid 源码、补 HAL 二进制或上板子**——这是镜像/板级工程，云上做不了也不该硬做。

### 42. lineage/RK3588 云手机镜像的额外差异项，对接魔云腾要处理（2026-11-15）

- **处理办法（对接魔云腾真机时做）**：对魔云腾的 A16 镜像做一个**轻量 build.prop 剥离层**——Docker FROM 它的镜像，改写 /system、/vendor、/product 的 build.prop，删掉/改掉 `ro.lineage.*`、`ro.build.host/user`、`ro.board.platform`、`ro.hardware` 等瑞芯微/lineage 痕迹（像我们验证 ro.hardware 时那样 COPY 改过的 build.prop，**不用编 AOSP，很轻**）。注意 ro.lineage.* 不能用启动参数清（会留空键，本身是差异项；且不能全局加到 disguiseProps，否则 stock redroid 上反而凭空多出空的 lineage 属性）——只能在那台镜像上改 build.prop。
- **结论**：魔云腾把硬件/GPU/基础镜像做完了，但它的镜像是"通用瑞芯微云手机"，带一批 lineage/rk3588 痕迹。我们的伪装层要在它的真镜像上加一个"build.prop 剥离层"把这些抹掉——这步必须等拿到魔云腾设备/镜像才能做（要读它真实的 build.prop）。

### 43. 带空格的启动参数会被截断（2026-11-15 实测确认）

### 44. ADB 体检发现的几处问题和修法（2026-11-16，POCO X4 GT 测试机实测）
- **时区/语言没跟代理走（出口香港、时区美东）**：「跟随代理」模式靠代理的检测结果（出口国家/时区），这个代理从没点过「检测」，结果为空就退回默认。**修法**：开机前和切换代理时，代理没检测过 / 失败 / 超过 6 小时就自动检测一次（`phones/proxyauto.go`，API 层 `RunProxyCheck` 共用）。实测重启后 timezone=Asia/Hong_Kong、locale=zh-HK，和出口一致。
- **刷新率 144 只报 15Hz**：实测 `androidboot.redroid_fps=144` → 屏幕模式 15Hz；60 / 120 正常（软件渲染下 120 时 SF 120Hz）。**修法**：超过 120 按 120 给（`redroidFPS`）。
- **/system/xbin/su、/.dockerenv**：Redroid 镜像自带 setuid 的 su，Docker 每次建容器都放 /.dockerenv。管家用 docker exec 本来就是 root，不需要 su，开机删掉。**坑**：刚 `docker start` 后马上 `docker exec rm` 会失败——安卓的程序都靠 `/apex/.../linker64`，init 挂好 /apex 之前任何 exec 都跑不了。改成后台每秒重试到成功（几秒内删掉，早于 App 启动）。
- **/proc/1/cmdline 带全部启动参数（qemu=1、redroid、所有覆盖属性）**：看着吓人，但安卓自己把 /proc 挂成 `hidepid=invisible,gid=3009`，App 和 adb shell 都看不到 1 号进程（实测 App uid 只看到自己 3 个 pid）。**不是 App 可见的差异项**，不用改；bind 覆盖 /proc/1/cmdline 也会失败（proc 下的 pid 目录不让挂）。
- **CPU 只剩 4 个 A55 小核**：宿主机 4 核、机型 8 核时以前从前往后截，天玑 8100 变成一台纯小核低端机。**修法**：`fitCPUs` 按比例缩、每组至少留 1 个、零头补给大核（4+4 → 2+2；4+3+1 → 2+1+1；核比组少时只留大核）。
- **ro.build.characteristics=default**：启动参数 `ro.build.characteristics=nosdcard` 实测**能生效**（#41 说的是写 build.prop 无效，启动参数可以）。
- **org.chromium.webview_shell**：AOSP 测试 App，真机没有。开机设置时 `pm uninstall --user 0` 卸掉（系统分区不动，`pm install-existing` 可恢复）。
- **其余（非容器能修，属镜像/板子阶段）**：ro.build.description 带空格（#43）、ro.hardware/ro.boot.redroid_*（#41）、uname 是 Oracle 内核、内存 24GB、uptime 100+ 天、SwiftShader 软件 GPU、没有传感器/摄像头/电话/WiFi、电池 level 0、GMS 缺 privapp 权限白名单导致开机崩溃（gapps 镜像要补 `privapp-permissions-google.xml`）、dalvik/bionic cpu variant=generic。
- **MAC 是「本地随机」格式不算差异项**：安卓 6 起 App 读 WiFi/蓝牙 MAC 都返回 02:00:00:00:00:00，安卓 10 起连 WiFi 默认就用随机 MAC，真机也是这个格式。

### 45. 管家重启会打断正在开机的手机的开机后设置（2026-11-16）
- **现象**：手机开机过程中管家被自动更新重启（GitHub 一有新提交，10 分钟内就会自动更新），开机后的后台步骤跟着中断：删 su / .dockerenv、开机设置（时区 / 语言 / settings / 电池 / 卸 webview_shell）、挂伪造文件。重启后没人补做，手机停在半配置状态（实测 webview_shell 没卸掉）。
- **修法**：
  1. 管家启动时 `ResumeRunning`：对每台容器在跑的手机重新做一遍（`phones/resume.go`）。三步都能重复做：rm -f 删过了也成功；设置已是目标值就跳过（不会无故重启安卓框架）；伪造文件看 `/.ppfake` 还在不在——在说明没挂完，接着挂，并跳过 `/proc/mounts` 里已挂上的；不在说明重启前已挂完，只按 `/proc/mounts` 恢复管理页显示的状态。

### 46. 谷歌服务崩溃、ADB unauthorized：两个功能问题（2026-11-16）
- **「谷歌测试」手机的 GMS 开机反复崩溃**（缺 MANAGE_USERS、找不到 gsf.gservices）：不是谷歌镜像的问题（`14.0.0_mindthegapps` 里 GmsCore / Phonesky / GoogleServicesFramework 和 privapp 权限文件都齐）。真正原因是这台手机的「带谷歌服务」开关是关的，跑的是普通镜像，GMS / Play 只是以前留在 /data 里的残留：没有 GSF、也没有特权权限，所以一直崩。打开开关重启后：GSF 在、GMS 拿到 MANAGE_USERS 等特权、开机零崩溃。
  - 管理页以前只有新建时能勾谷歌服务，**已建好的手机没法切换**——信息页加了「谷歌服务」开关（下次开机生效）。
  - 关着谷歌服务、/data 里却有 GMS 时，开机设置会提示（不自动删，可能有账号数据）。
- **ADB 连上是 unauthorized**：开机参数 `ro.debuggable=0`（真机出厂值）让 adbd 强制校验电脑公钥（`ro.adb.secure` 显示 0 也没用）。#33 写的「不用授权」已经不对了。真机是在手机上点「允许」，云手机改成：管理页 ADB 窗口把电脑的 `adbkey.pub` 粘贴进去，管家写进手机 `/data/misc/adb/adb_keys`（`POST /api/phones/{id}/adb-key`，公钥格式和长度 524 字节先校验，作为参数传给 sh，不拼命令）。/data 在容器外，开关机都保留；重置手机后要重新授权。
- **CPU 类型属性**：由 generic 改成 cortex-a76（开发机 Neoverse N1、板子 RK3588 都是 A76 一类）。`ro.bionic.cpu_variant` 用开机参数改得动；`dalvik.vm.isa.*.variant` 不是 ro 属性，开机参数会被 build.prop 盖回 generic，改成开机设置里 setprop（只改已存在的）。`ro.bionic.2nd_cpu_variant`（谷歌镜像带 32 位才有）开机后改不了、开机参数会给 64 位镜像凭空加出这个属性，留 generic。
- **没修、也不该硬修的**：uptime（100+ 天）和总内存（24GB）读的是宿主机内核。lxcfs 能改 /proc/uptime、/proc/meminfo，但 App 常用的 `SystemClock.elapsedRealtime()`（CLOCK_BOOTTIME）和 `sysinfo()` 直接问内核、改不了，只改一半反而前后矛盾，比不改更容易被看出来。彻底办法是时间命名空间（CLOCK_BOOTTIME 偏移）+ 内存按机型限额，属运行时 / 板子阶段。

### 47. dumpsys battery 设不了健康度 / 电压 / 电池类型（2026-11-16 实测）
- 体检看到电池 `present: false`、`health: 1（未知）`、`technology` 空——真机分别是 true、2（良好）、Li-ion。
- 安卓 14 的 `dumpsys battery set` 只支持 ac / usb / wireless / dock / status / level / temp / present / counter / invalid。`set health 2`、`set voltage 4100` 会打印 `Unknown set option` **但退出码还是 0**——以前代码以为设上了，其实没生效。
- **修法**：开机设置加 `set present 1`（实测生效）；去掉不生效的 health 命令（不假装设过）。健康度 / 电压 / 电池类型要等镜像阶段补一个假的电池 HAL（health HAL 读 /sys/class/power_supply，容器里没有）。
- **大坑（实测）**：Redroid 刚开机电池是 `level 0、没插电、present=false`。这时设 `present 1`，安卓认为「有电池且没电」→ **3 秒内自动关机**（容器以 130 退出：pid 命名空间里的 init 调 reboot(POWER_OFF) 会被 SIGINT 杀掉；重启是 SIGHUP / 129）。所以开机设置必须**先设电量（档案没填用 50，最少 1）再设 present**，有单测保证顺序。以后看到容器 exit 130 先想到「安卓自己关机了」，查电池 / 温度。

### 48. 蓝牙：开机连崩 → 自己编蓝牙芯片模拟器（2026-11-16 / 17）
- 现象：logcat -b crash 里 `bluetooth@1.1-service` 和 `com.android.bluetooth`（bt_stack_manage）各 SIGABRT 好几次（Failed HIDL return status），之后蓝牙停在 OFF。
- 原因：AOSP 默认 `settings global bluetooth_on=1`，BluetoothManagerService 开机「Auto-enabling Bluetooth」；容器里没有蓝牙硬件，HAL 一起就崩，重试几次放弃。
- 修法：开机设置里 `settings put global bluetooth_on 0`（已是 0 就跳过）。第一次开机还会崩一轮（设置是开机后才做的），之后每次开机不再自动开蓝牙、不再崩。蓝牙关着和真机常见状态一致。真要蓝牙得等板子 / 蓝牙 HAL。
- **深挖（2026-11-16）**：Redroid 的蓝牙 HAL 是 AOSP 的纯软件蓝牙芯片模拟（rootcanal，`android.hardware.bluetooth@1.1-service.sim`），**原版 Redroid 14 一样崩**，不是我们改出来的。第一处崩在解析它自己的默认地址（`Invalid address: 3C:5A:B4:01:02:03`，源码逻辑没问题，是这份编译产物的问题）；把那条判断改成 nop 后又在 `LinkLayerController::Reset` 里 CFI 校验失败崩掉 → 这个二进制打补丁修不完。
- **解决（2026-11-17，安卓 14 / 15）**：
  - 自己编 rootcanal：`host/build-rootcanal.sh`（google/rootcanal，Bazel，锁定版本；官方只给 x86 / macOS 现成程序，arm64 要自己编，4 核约半小时；官方说明里的 pdl-compiler 用不到，arm64 上也编不过，不装）。补丁：环境变量 `PP_BT_ADDR` 指定芯片地址。装到 `/usr/local/bin/pp-rootcanal`。
  - 镜像：安卓 14 起模拟器的蓝牙 HAL（`android.hardware.bluetooth-service.default`，AIDL）是串口说 H4，串口路径看属性 `vendor.ser.bt-uart` → 镜像里设成 `/dev/ttyS1`，删掉 Redroid 的坏 HAL；标签 `prism.bt=1`。
  - 小助手在 /dev/ttyS1 放伪终端（root:bluetooth 0660），转到 127.0.0.1:6402；管家开机在这台手机的网络命名空间里用 systemd 临时服务起 rootcanal（`ppbt-<id>`，nsenter -n），地址用机型档案的蓝牙 MAC，关机 / 删除时停。每台手机一个，互相看不到。有芯片就不再强制 bluetooth_on=0。
  - 蓝牙名字：第一次打开时取 `bluetooth.device.default_name`（没有就用 ro.product.model），管家把设备名写进 build.prop。
  - **实测（安卓 14）**：开机蓝牙自动打开，地址 = 指定的 MAC，名字 = 设备名（POCO X4 GT），关了再开正常（重开约 3 秒），零崩溃。
- **安卓 13**：模拟器的蓝牙 HAL（btlinux）走 Linux 内核蓝牙（HCI user channel），内核蓝牙不支持网络命名空间（容器里建不了蓝牙 socket）→ 容器里走不通，照旧关着。板子阶段看 cnflysky 镜像自带的蓝牙，或给安卓 13 移植串口 HAL。
- **小毛病**：rootcanal 在手机网络里听 6401–6404 端口（本机能连上），和电话的 9600 一样，App 扫本机端口能看到；以后可以只留 6402 并限制来源。

### 49. 开机时长 100 多天：用时间命名空间归零（2026-11-16 实测通过）
- **现象**：安卓里 `uptime` 显示 111 天（宿主机开了多久），云手机「刚开机」却开了几个月，很假。
- **为什么不用 lxcfs**：lxcfs 只能改 /proc/uptime 文件，App 常用的 `SystemClock.elapsedRealtime()`（CLOCK_BOOTTIME）、`uptimeMillis()`（CLOCK_MONOTONIC）直接问内核（vdso），改不了——只改一半前后矛盾，比不改更假。
- **办法**：Linux 5.6+ 的时间命名空间（`CONFIG_TIME_NS`）给命名空间里的 MONOTONIC / BOOTTIME 加偏移，vdso、/proc/uptime、/proc/stat 的 btime、sysinfo 全都一致。Docker 不支持直接开，所以**管家程序自己当容器启动器**（静态编译，安卓容器里能直接跑）：容器入口改成 `/pp-init pp-init 0 /init <镜像原入口参数>`，它 `unshare(CLONE_NEWTIME)`、写 `/proc/self/timens_offsets`，再 exec 安卓 init（`agent/internal/timens`）。管家程序文件只读挂到 `/pp-init`，开机后卸掉并删掉挂载点，不留文件。内核不支持或建命名空间失败就照常开机；`-no-timens` 参数可整体关掉。
- **实测**（adb shell，和 App 同一视角）：`uptime` = up 3 min、`/proc/uptime` = 206 秒、btime 变成这次开机时间、`dumpsys alarm` 的 nowELAPSED 从 0 开始；开机正常、零崩溃。
- **注意**：`docker exec` 进容器**不会进时间命名空间**（runc 不知道它），所以用 docker exec 读 /proc/uptime 还是宿主机的值——验证要用 adb shell。管家用 docker exec 跑的东西（如剪贴板 app_process）看到的是宿主机时钟，不影响 App。
- **残留**：`/proc/uptime` 第二列（所有 CPU 空闲时间累计）内核没按命名空间调整，还是宿主机的累计值（远大于 开机时长×核数），极少有检测看这个。
- 板子：`host/check-board.sh` 加了 CONFIG_TIME_NS 检查（RK3588 的 5.10 / 6.1 内核要看编译配置有没有开）。
- **补充（同日）**：这台测试机来回切过普通镜像 / 谷歌镜像，/data 里留着另一套系统的 App 数据，谷歌搜索 App 开机崩（`A migration from 6 to 5 was required`：数据库比 App 新，版本倒退）。不是代码问题，新建的手机不会有；`pm clear com.google.android.googlequicksearchbox` 后重启零崩溃。管理页谷歌服务开关旁边加了提示：来回切换后有 App 一直崩就重置手机。

### 50. 开了时间命名空间后，新手机实时画面 0 字节（2026-11-16，itest 发现）
- **现象**：`host/itest-api.sh` 的「视频流」一项失败：新建的手机 8 秒收到 0 字节（老手机正常）。手动对比：`docker exec screenrecord` → 0 字节；`nsenter -t <容器PID> -a`（含时间命名空间）跑同样的 screenrecord → 1.5 MB。
- **原因**：#49 让安卓活在自己的时间命名空间里，但 `docker exec` 起的进程还在宿主机的时间里（runc 不知道时间命名空间），时钟差了宿主机开机时长（100 多天）。screenrecord 要和 SurfaceFlinger / 编码器对时间戳，帧对不上就一帧都不出。
- **修法**：对时间敏感的命令改用宿主机 `nsenter -t <PID> -a -- /system/bin/env -i PATH=… 命令` 进容器全部命名空间来跑（`phones/timensexec.go` 的 phoneCommand；实时画面已改）。没开时间命名空间、拿不到 PID、宿主机没有 nsenter 时自动退回 docker exec。nsenter 要 util-linux 2.36+ 才有时间命名空间（Ubuntu 22.04 起都有）。
- **注意**：nsenter 起的进程不在容器的 cgroup 里（CPU / 内存算在管家头上）；screenrecord 本身很轻（编码在容器里的 media.swcodec），可以接受。以后再有「docker exec 跑出来结果怪」的，先想时间命名空间。

### 51. 走香港代理的手机被报「上不了外网」：两层原因（2026-11-16）
管理页顶部一直红：「gapps测试 上不了外网」。实际查下来手机能上网（在手机网络里 curl 返回 204 / 200），是两个问题叠在一起：
1. **DNS 被透明代理截走（真问题）**：nft 的 `pp_tproxy`（mangle 优先级）比 `pp_dns`（dstnat）先执行，手机发往 53 端口的 DNS 先被 tproxy 截走、当普通 UDP 交给代理节点；节点不支持 UDP（很多住宅 / 机场节点都不支持）时，用普通 DNS 的程序全部解析失败（`dig @8.8.8.8` 超时）。安卓系统自己碰巧用的是加密 DNS（DoT，TCP 853），所以 App 大多不受影响，问题被掩盖了。**修法**：`host/network.sh` 的 pp_tproxy 里先 `meta l4proto { tcp, udp } th dport 53 return`，让 DNS 落到 pp_dns 交给 mihomo。实测 `dig @8.8.8.8` 恢复，宿主机网络不受影响（apply → 验证 → confirm）。
2. **检测命令本身对慢代理不灵（误报）**：`printf 请求 | nc 主机 80`，toybox nc 读到输入结束就断开、不等回应（`-q` 参数不起作用，实测 50ms 就退）。直连时回应快碰巧收得到，走约 1 秒延迟的代理就永远是空。**修法**：`(printf 请求; sleep 10) | nc …`，实测收到 `HTTP/1.1 204`；单台检查固定约 10 秒，后台 4 台并发、超时放到 30 秒。
- 教训：itest 的「能上外网」只用了「直连（仅开发）」，测不出走真实代理的问题。以后验证网络改动，要拿一台走真实（最好是不支持 UDP 的）代理的手机测。

### 53. 手机里看到的存储总容量是宿主机整块盘（2026-11-16）
- **现象**：手机里 `df /data`、设置 → 存储 显示的是宿主机的盘（开发机 183GB），真手机是 128 / 256 / 512GB 这种整数。
- **修法**（`phones/storage.go`）：新建（或重置后）的手机，开机前按机型档案的 `storageTotal`（GB，十进制，和厂商标的一样）建一个 **ext4 稀疏磁盘镜像** `phones/<id>/data.img`，`mount -o loop` 到 `phones/<id>/data` 再挂进容器。稀疏文件只有真正写进去的数据才占宿主机空间（`mkfs.ext4 -m 0 -E lazy_itable_init=1,lazy_journal_init=1`，空手机几十 MB）。
- **不碰老手机**：数据目录里已经有东西、没有镜像的手机保持原来的目录方式，**不迁移数据**；重置后（旧数据进回收站）自动换成镜像。删除 / 重置前先 `umount`（不行就 `umount -l`）。回收站大小改成按实际占用的磁盘块算（稀疏镜像表面大小 256GB）。
- **注意**：
  - 镜像是超额分配：几台 256GB 的手机加起来可以超过宿主机实际空间，真写满宿主机盘时手机里会报写入错误——和原来共用一块盘的风险一样，看宿主机剩余空间（自检有「硬盘剩余」）。
  - 宿主机重启后镜像没挂，开机时管家会自动再挂。`-no-data-images` 可整体关掉。

### 54. 内存：按机型上限 + lxcfs 显示（2026-11-16 用户定提到 8GB）
- **以前**：每台容器固定 3GB 上限，手机里 /proc/meminfo 却显示宿主机 24GB（机型档案写 8GB），三个数对不上。
- **现在**（`phones/memory.go`）：
  - 容器内存上限 = 机型档案 `memTotal`（GB 十进制：8GB ≈ 7629 MiB，真 8GB 手机 MemTotal 也是 7.x GiB），封顶「宿主机内存 - 3GB」。`-mem-follow-model=false` 退回固定 `-mem-mb`。
  - **开机前内存把关**：正在运行的手机上限之和 + 这台 > 宿主机内存 - 3GB 就不让开（提示先关一台）。阿什本 24GB：8GB 的手机同时 2 台。以前 4 台 × 3GB 的上限也就不需要了（MaxRunning 仍在，两个条件都要满足）。
  - **lxcfs**：宿主机装 lxcfs（`host/setup-host.sh` 已加），开机时把 `/var/lib/lxcfs/proc` 只读挂进容器 `/.pplxcfs`，开机后 `mount --bind /.pplxcfs/meminfo /proc/meminfo`、再卸掉临时挂载点（和 fakefs 一样不留痕迹）。lxcfs 按读的进程所在 cgroup 往上找最小的内存上限，安卓自己在容器里建的子 cgroup 也能对上。
- **lxcfs 不能随便重启**：一重启，正在运行的手机里 /proc/meminfo 就读不了（FUSE 断开），lmkd 等会出问题。所以 `apt-mark hold lxcfs`，要升级挑没开手机的时候做。
- **改不了的**：`sysinfo()` 系统调用（部分原生代码、`free` 命令）仍返回宿主机内存；安卓 ActivityManager 的总内存读的是 /proc/meminfo，已经对上。
- **补充（同日，网上找数据）**：用户暂不买真机，从公开数据补：
  - **屏幕密度**：从真机 build.prop 的 `ro.sf.lcd_density` 改对 4 款（档案以前填的是像素密度 ppi 或估计值）：Nothing 2a 395→420，Xiaomi 13T / 12T / Redmi Note 13 Pro+ 446→480；POCO X4 GT 440、realme 480 原来就对。
  - **更多分区数据**（GitHub 上别人用 dumpyara 做的整机转储，`host/fetch-dump-buildprops.sh` 浅克隆只取 build.prop）：Redmi Note 13 Pro+ 安卓 15（SLEZxE-dumps/redmi_zircon_dump）、Nothing 2a 安卓 15（RandomPush/nothing_pacman_dump）、POCO X4 GT 安卓 14（Jiovanni-dump/poco_xaga_dump，版本和原指纹一致）、Xiaomi 12T 安卓 14 换成全球版（Jiovanni-dump/xiaomi_plato_dump）。安卓 15 指纹也换成和转储同一版（原来的是设备树里抄的另一版，版本号对不上）。
  - **一份固件带好几个型号 / 地区**：小米固件里有 vendor/xaga_build.prop、xagapro_build.prop……（按 `ro.boot.product.hardware.sku` 只导入一个），Nothing 有 odm/etc/build_EEA.prop 等（按地区导入）。提取脚本加了 `--sku` / `--region`，默认地区文件都不读（全球版）。

  - **官方完整包自己拆**（网上没有现成转储的）：`host/ota-buildprops.sh <完整包 URL> <输出目录>`，在阿什本下载小米官方 recovery 完整包（约 6GB），payload-dumper-go 只拆身份相关的 9 个分区，只读取出 build.prop，临时文件删掉。Xiaomi 13T 安卓 15（OS2.0.214.0.VMFMIXM）、Xiaomi 12T 安卓 15（OS2.0.202.0.VLQMIXM）已用这个办法录入，都是全球版。坑：① 官方 bigota.d.miui.com 从阿什本只有几十 KB/s，换 bn.d.miui.com 实测 9MB/s；② 小米分区是 erofs，第一次直接 `mount` 全失败（要 `-t erofs`），而且脚本跑完把 6GB 临时文件删了只能重下——改成「取到足够文件才删」；③ erofs-utils 1.7 的 dump.erofs 没有 `--cat`，读不了单个文件，用 `fsck.erofs --extract` 兜底。

### 57. 手机里只有有线网卡 eth0，没有 WiFi（2026-11-16）
- **差异项**：Redroid 手机里只有 `eth0`，安卓看到的网络类型是「以太网」（Ethernet），没有 wlan0、WiFi MAC、SSID；真手机几乎都走 WiFi 或流量。
- **做法**（`agent/internal/wifi`、`agent/internal/phones/wifi.go`、`host/build-wifi-image.sh`）：
  - **镜像**：Redroid 没带 WiFi HAL。从谷歌官方安卓模拟器镜像（同版本、arm64、纯 AOSP）的 vendor 分区拷 WiFi HAL、wpa_supplicant、hostapd 和递归缺的库，产出 `<原镜像>-wifi`（标签 `prism.wifi=1`）。管家看到这个标签才给手机配 WiFi，否则照旧走 eth0。
  - **宿主机**：内核自带的 WiFi 模拟器 `mac80211_hwsim`（安卓官方模拟器也用它）。每台手机一对虚拟网卡（netlink 按需建，`radios=0` 不自动建）：一块搬进手机当 `wlan0`（MAC = 机型档案 wifiMac），一块留在这台手机自己的「路由器」网络命名空间 `ppr-<ID>` 里当热点（hostapd WPA2、SSID 像 `TP-Link_XXXX`、dnsmasq 发地址、NAT）。路由器的上行就是 Docker 原来分给手机的 eth0，所以网络模块按 IP 分流到代理的规则完全不变。
  - **隔离**：hwsim 的虚拟电波只在同一个 netgroup 里互通，netgroup 按建网卡时所在的命名空间分 → 两块网卡都在这台手机的路由器命名空间里建，手机之间互相扫不到。
  - 开机设置里 `cmd wifi connect-network <SSID> wpa2 <密码>`，安卓把配置存进 /data，以后自动连。
- **踩到的坑**（按顺序）：
  1. 模拟器的 WiFi 程序缺 vendor 库（keystore2、keymint、secureclock…）→ 构建脚本按 `readelf NEEDED` 递归补齐。
  2. 有 eth0 时安卓觉得「已经有网」，根本不去请求 WiFi → 必须把 eth0 从手机里拿走（搬进路由器命名空间）。
  3. 热点和手机在同一命名空间时，回包被当成「火星包」丢掉 → 分开命名空间。
  4. wpa_supplicant 报「扫描结果不够新」连不上：手机在时间命名空间里（开机时间是假的，#50），内核给的扫描时间戳是宿主机的 → 加一个 `LD_PRELOAD` 时钟垫片 `libppclock.so`（`host/wifi/ppclock.c`），把时间偏移加回去。
  5. `iw phy <名字>` 在容器里找不到网卡（sysfs 不对）→ 先在路由器里建好 `wlan0` 再把网卡搬进手机。
  6. 网络命名空间删了，hwsim 网卡不会跟着删 → 关机时显式按名字删（netlink DEL_RADIO，要在网卡当前所在的命名空间里发）；配置失败时也把已搬进手机的那块删掉（不然手机里留一块没用的 wlan0）。
  7. **WPA2 热点起不来**，hostapd 报 `nl80211: kernel reports: key addition failed`（开放热点正常）：一度以为是 hostapd 2.10 太老，编译了 2.11 照样失败。**真正原因：WPA2 用的 AES-CCMP 加密算法 `ccm` 内核模块没加载**（这台 Oracle 内核不自动加载，`/proc/crypto` 里没有 ccm）。`modprobe ccm` 后系统自带的 2.10 就正常。管家检查宿主机时自动加载，`setup-host.sh` 写进开机自动加载。
  8. **管家一重启（自动更新），手机就断 WiFi**：hostapd / dnsmasq 是管家起的子进程，systemd 重启管家服务时会把服务里的进程全杀掉。→ 改成各起一个临时 systemd 服务（`systemd-run --unit=ppwifi-<ID>-hostapd`，`Restart=always`），不受管家重启影响，挂了自动拉起；管家重启后和每 2 分钟的上网检查前还会检查一遍，没在跑就补起来（`wifi.EnsureDaemons`）。
  9. 手机走 WiFi 后 eth0 不在容器里了，`docker stats` 读网卡统计失败，**整份统计全是 0**（管理页 CPU / 内存占用不显示）→ Docker 给的是空的就直接读容器的 cgroup 文件（`docker/cgroup.go`）。
  11. **快速关机再开机（含一键重置）偶尔退回有线**，日志「手机 wlan0：No such file or directory」：手机关机后内核把它那块网卡还回宿主机是异步的，马上再开机时旧网卡还占着同名，新网卡被内核悄悄改名成 phyN，按名字找不到（之前加的「稍等重试」没用，不是时机问题）。→ 每次开机网卡名加 4 位随机后缀，名字记在 wifi/radios；关机和下次开机前按记录、并按这台手机的名字前缀清掉宿主机上漏下的网卡。实测连续关机再开机 3 次都连上 WiFi，宿主机零残留。
  10. 实时画面关掉后 screenrecord 还在跑：nsenter 进 PID 命名空间时会 fork，杀 nsenter 杀不到 screenrecord → 放进单独的进程组，整组杀（`timensexec.go`）。
- **实测（阿什本，2026-11-16）**：手机里只有 `lo` + `wlan0`；`cmd wifi status` 连上 `TP-Link_752D`，wpa2-psk，RSSI -30，安卓网络类型 WIFI；没有 eth0；generate_204 正常、出口香港、联网验证 VALIDATED；`itest-api.sh` 32 项全过。两台 WiFi 手机同时开，各自只扫得到自己的热点（隔离成立）；删手机后命名空间、网卡、进程都清干净。
- **安卓 15**：`bash host/build-wifi-image.sh redroid/redroid:15.0.0_64only-latest 15` 一次成功（模拟器 35_r02，补了 11 个库），新建 A15 手机实测只有 wlan0、WPA2 连上、VALIDATED、204、无崩溃。阿什本 agent.env 安卓 14 / 15 / 谷歌 14 三个镜像都已是 `-wifi` 版。
- **管家重启实测**：部署新版后自动发现老手机的热点没在跑并拉起；再手动重启管家，WiFi 不断；ADB 经路由器转发 `adb devices` 显示 device。

### 58. 云手机开机会改宿主机自己的内核设置（2026-11-16，稳定性测试时发现）
- **现象**：两台手机才用约 2GB 内存，宿主机「可用内存」却只有 4.7GB；之前 WiFi 的 `ccm` 模块也一直不会自动加载。
- **原因**：手机是特权容器，安卓 init.rc 里一堆 `write /proc/sys/...` 直接写到了宿主机的全局设置（`net.*` 是每台手机自己的网络命名空间，不受影响；`kernel.*`、`vm.*`、`abi.*` 是整台机器共用的）。阿什本实测被改成：
  - `kernel.modprobe` 被清空 → **宿主机不能自动加载内核模块**（#57 的 ccm 就是这么来的）；
  - `kernel.panic_on_oops=1`（而 `kernel.panic=0`）→ 内核一出错**整台机器死机且不会自己重启 = 失联**；
  - `vm.watermark_scale_factor=1795`（安卓的 extra_free_kbytes.sh 按屏幕大小算的，默认 10）→ 内核替安卓预留约 7GB 空闲内存，宿主机「可用」少一大截；
  - `vm.overcommit_memory=1`、`kernel.perf_event_paranoid=-1`（降低宿主机安全）、`kernel.hung_task_timeout_secs=0`、`kernel.sysrq=0`、`kernel.kptr_restrict=2` 等。
- **为什么不能直接挡**：安卓 init 会在容器里重新挂一个 proc 到 /proc（`hidepid=invisible`），开机前把 /proc/sys 设成只读会被盖掉；改成非特权容器是大改动。
- **修法**（`agent/internal/hostguard`）：管家守一张「宿主机应有的值」表（Ubuntu / 内核默认值），启动时、每台手机开机后、以后每 30 秒，被改了就改回来并记日志；同时写 `/etc/sysctl.d/90-prism-phone-host.conf`，宿主机重启也对。另外加了 `kernel.panic=10`：万一真死机，10 秒后自动重启，不失联。`-no-host-guard` 可关。
- **代价**：手机开机到管家改回之间有几秒到几十秒的窗口；手机里 `cat /proc/sys/vm/...` 看到的也是宿主机的值（本来就是）。
- 测试：`hostguard_test.go`；`itest-api.sh` 加了「宿主机内核设置没被手机改掉」。

### 59. 传感器：用模拟器的传感器 HAL + 我们自己喂数据（2026-11-16，原型已通）
- **目标**：手机里没有任何传感器（真机都有加速度、陀螺仪、磁力计、距离、光线……），App 一查就露馅。
- **思路**：谷歌官方安卓模拟器的 vendor 里有完整的传感器 HAL（`android.hardware.sensors-service.multihal` + 插件 `android.hardware.sensors@2.1-impl.ranchu.so`），数据来自模拟器的「qemud 传感器管道」。我们在容器里放一个伪终端（pty）当这个管道（`/dev/goldfish_pipe_dprctd`），自己扮演模拟器发数据。
- **协议**（`device/generic/goldfish/hals/sensors`）：每条消息 = 4 位十六进制长度 + 内容。HAL 先写 `pipe:qemud:sensors\0`，再发 `time:<ns>`、`list-sensors`（我们回一个掩码，决定有哪些传感器：0 加速度、1 陀螺仪、2 磁场、3 方向、4 温度、5 距离、6 光线、7 气压、8 湿度…）、`set:<名字>:<0|1>`、`set-delay:<毫秒>`；我们发 `acceleration:x:y:z`、`gyroscope:…`、`magnetic-field:…`、`proximity:5.0`、`light:180` 等。原型：`host/sensors/feeder-poc.py`。
- **坑 1：这版 HAL 只走 vsock**（连宿主 CID 2 端口 5000），失败直接放弃，不再试管道文件（反汇编 `qemu_pipe_open_ns`：只有图形类管道才走 `/dev/goldfish_pipe_dprctd`）。vsock 不分容器、在甲骨文虚拟机上直接连到云厂商的虚拟机管理程序，没法接管。→ **改一条指令**：把 vsock 分支开头的 `mov w0,#0x1388`（安卓 14 r04 的 ranchu.so 在 0x16dc4）改成跳到打开管道文件的那段（0x16e00），`b +0x3c`。
- **原型实测（阿什本，独立测试容器）**：HAL 正常起来，安卓列出 5 个硬件传感器 + 系统自带的融合传感器（重力、旋转矢量、游戏旋转矢量、校正陀螺仪），有客户端在按 66ms 读数据。
- **已落地**（阿什本实测安卓 14、15 都通）：
  - 镜像：`build-wifi-image.sh` 同时加传感器 HAL，自动打补丁（`host/sensors/patch-ranchu.py` 按指令特征找位置，安卓 14 在 0x16dc4、15 在 0xe4b8，都找对了），标签 `prism.sensors=1`。阿什本三个镜像（14、15、谷歌 14）都已重建。
  - 名字：模拟器名字（Goldfish…）和厂商（The Android Open Source Project）原地换成通用名（Accelerometer、Gyroscope、Magnetometer、Proximity Sensor、Light Sensor 及未校准版，厂商 MTK）。**通用名是临时的**：各机型真实芯片名要真机 `dumpsys sensorservice`，公开规格只给类型。
  - 喂数据：管家开机时把配置（种子、地磁、时区）作为 `--sensors=` 传给 pp-init；pp-init 在安卓 init 之前开伪终端、绑到管道路径、起喂数据子进程（`internal/sensors`，进程名 vendor.sensord）。它活在容器里，跟手机同生共死，管家重启不影响。HAL 重启时先清掉没读走的旧数据再回答 list-sensors（不然新 HAL 读错崩溃）。
  - 数据：手机平放桌上（±2.5° 随机倾斜、随机朝向，每台不同、开机之间不变），加速度噪声 0.012 m/s²，陀螺仪噪声 0.0012 rad/s + 未校准版带零偏，地磁按代理出口地区（香港约 46µT），磁力计未校准版带硬铁偏移，距离一直是「远」，光线按当地时间（白天 150–400 lux、晚上 90、夜里 4）。
  - 实测：安卓列出 8 个硬件传感器（加速度、陀螺仪、磁力计、距离、光线 + 3 个未校准）+ 系统融合的重力、线性加速度、旋转矢量、方向等；加速度读数 `0.09, -0.33, 9.77` 一类，时间戳从开机算起。
- **管家实测（2026-11-16）**：两台管家开的手机（安卓 14 谷歌、安卓 15）都有 8 个硬件传感器且有数据，磁力计约 46µT（香港），WiFi 同时正常；`itest-api.sh` 33 项全过；手机里进程名 vendor.sensord，根目录和挂载表里没有 /pp-init（开始忘了：喂数据进程占着 /pp-init，普通 umount 报忙，改成 umount -l）。
- **还没做**：各机型的传感器清单（有没有气压计等）和量程（距离量程现在是 1.0、加速度量程 39.3 是模拟器值，真机常见 5.0 / 78.4）——要么按机型打补丁，要么真机数据到了再改。

### 61. 手机里没有触摸屏：点击滑动是 input 命令注入的（2026-11-16）
- **差异项**：`dumpsys input` 里只有一个虚拟键盘，没有任何触摸设备；`pm list features` 只有 touchscreen / faketouch，没有多点触控（真机都有 multitouch / distinct / jazzhand）。管理页的点击滑动走 `input tap/swipe`，不来自任何设备，按压力度、接触面积永远一样，滑动是匀速直线。
- **做法**（`agent/internal/touch`）：手机里的小助手进程（vendor.sensord，pp-init 开机前起，和传感器同一个）用内核 uinput 建一块 10 点触控屏（名字 fts_ts、总线 I2C、INPUT_PROP_DIRECT、ABS_MT_* 坐标范围 = 屏幕像素），在容器 /dev/input 下建设备节点；管家把点击 / 滑动通过抽象 unix socket `@vendor.sensord`（进手机网络命名空间连，不落文件）发给它，它像真手指一样做：落点 1~2 像素偏差、按住 50~110ms 中间轻微挪动、力度和接触面积每帧有变化；滑动 120Hz 采样、先快后慢、带一点弧度和抖动。小助手不在（老镜像、`-no-sensors`）就退回 input 命令。镜像里加 `android.hardware.touchscreen.multitouch.jazzhand.xml`（标签 prism.touch=1）。
- **坑 1**：设备节点被删——开机时我们建好的 /dev/input/eventN 不见了：Redroid 的 `redroid.common.rc` 在 early-init 里 `rm -rf /dev/input` 再 `mkdir`（查实）。→ 小助手每 2 秒看一眼，没了就重建。
- **坑 2**：安卓报 `EventHub: could not open /dev/input/event4, Permission denied`，root 和 uid 1000 在 shell 里都能打开。原因：EventHub 用 inotify 盯 /dev/input，文件一出现就去打开、失败不再重试；我们是先建（默认权限）再改属主权限，它正好卡在中间。→ 建的那一刻就用 0666（umask 清零），3 秒后（它已打开）再收紧成真机一样的 root:input 0660。
- **实测（阿什本独立测试容器，安卓 15）**：`dumpsys input` 有 `Device 2: fts_ts`，Classes TOUCH | TOUCH_MT，Sources TOUCHSCREEN，DIRECT 模式、内置屏；`pm list features` 有 multitouch / distinct / jazzhand；点设置页搜索栏打开了搜索页；桌面上滑打开了全部应用。
- **还没做**：管家开的手机要重建镜像后重启才有（稳定性测试结束后）；触控芯片名按机型（现在都叫 fts_ts，档案字段 touchName 可改）。

### 62. 电脑键盘打字带出来的差异项（2026-11-16 用户问到，已修）
- **打字太快**：电脑上打的一串英文攒一起 `input text` 一次发，几毫秒打完几十个字，统计打字节奏的 App 能看出来不是人。→ 打字（`human: true`）改成一个字一个字发，字间隔 70~220ms，空格和标点后再多停一下（安卓 12 起 input 是 cmd input 的壳，单次十几毫秒，节奏由 sleep 决定）。管理页「发送」框的长段文字仍然一次粘贴（那就是粘贴）。
- **中文走剪贴板**：每个词都改写手机剪贴板再粘贴，剪贴板里留着我们打的字。→ 粘贴完把手机原来的剪贴板内容放回去（原来是空的没法「放回空」）。中文整词一次上屏，和真输入法提交一个词是一样的。
- **剪贴板自动同步弹提示**：管理页每 3 秒以 shell 身份读手机剪贴板；安卓 13 起，别的 App 复制的内容被另一个 App 读，会弹「XX 已从剪贴板粘贴」（ClipboardService.showAccessNotificationLocked），shell 没有 SUPPRESS_CLIPBOARD_ACCESS_NOTIFICATION，`pm grant` 也给不了（not a changeable permission type）。→ 开机设置里把 `secure clipboard_show_access_notifications` 设成 0（设置 → 隐私里用户自己能关的开关），中文粘贴也不再弹提示。
- **还剩的**：中文是「粘贴」而不是输入法提交（App 能收到一次粘贴动作）；要彻底像真人只能装中文输入法（项目规矩不装）。

### 64. uname() 是宿主机内核（2026-11-16，已修）
- **原因**：uname 的 release / version 来自进程的 UTS 命名空间。Docker 给每个容器新建一个，但内容是从宿主机复制的，只有主机名有系统调用能改，版本号改不了。fakefs 只能改 /proc/version 这类文件。
- **修法**：内核模块 `pp_uts`（`host/kmod/pp_uts`，`host/build-kmod.sh` 编译安装、开机自动加载，`setup-host.sh` 里自动跑）：提供 /proc/pp_uts（只有 root 能写），写 `<容器 init 的 pid>|<release>|<version>` 就改这个容器的 UTS 命名空间，拒绝改宿主机的（init_uts_ns）。管家每台手机启动后马上写这台的 kernelRelease / kernelBuild（机型档案字段，按真实范围随机）。没有模块就跳过。
- **实测（阿什本）**：模块编译加载正常（内核 6.17.0-1018-oracle，没有 Secure Boot、不强制签名）；测试手机里 `uname -a` = `Linux localhost 5.10.198-android12-9-o-… #1 SMP PREEMPT … aarch64`，/proc/sys/kernel/osrelease 一样；宿主机自己的 uname 不变；对 pid 1 写被拒绝。
- **板子上**：要板子内核的头文件（厂商 SDK / 内核源码）重新编译这个模块。

### 65. 电话和 SIM 卡（2026-11-16，安卓 13 / 14 / 15 都打通）
- **目标**：真手机就算没插卡也有电话子系统；插了卡还有运营商、信号、IMEI / IMSI / ICCID。Redroid 默认 `ro.radio.noril=yes`，电话整个关着，也没声明 telephony 能力。
- **基带模拟**（`agent/internal/modem`）：手机里的小助手扮演基带回 AT 命令（SIM 就绪、注册到运营商、信号、IMEI / IMSI / ICCID、SIM 文件 EF_ICCID / EF_SPN / EF_AD 等），运营商按代理国家选真实的（带真实 MCC/MNC），IMEI / ICCID 带 Luhn 校验位，按 androidId 播种（一键新机换卡）。单元测试齐。镜像去掉 noril、声明 telephony 能力（7 项），管家开机把移动数据关掉。
- **坑 1：Redroid 自带的 rild 框架不认**。安卓 13 起框架只认电话接口 1.4 以上（日志「IRadio <1.4 is no longer supported」），Redroid 自带 libril 是 1.1 → 手机像没插卡。
- **坑 2：模拟器的新版 rild**（libgoldfish-rild + libril-modem-lib，接口 2.x）按名字加载 libcuttlefish-ril-2.so。它支持三种连基带的方式：vsock（默认，云上连不到）、`-d 串口`、`-p 端口`（连本机 TCP）。**用 `-p 9600`**：小助手在手机的网络命名空间里听 127.0.0.1:9600（`agent/sensorsmode.go` serveModemTCP）。
- **坑 3：cuttlefish RIL 读空指针崩溃**（`requestFacilityLock+328`）。它用「多行」方式发的查询（`AT+CLCK=...,2,...`、`AT+CPINR=...`）不检查有没有内容行，基带只回 OK 就读空指针。→ 基带对这些必须回内容行（`+CLCK: 0`、`+CPINR: SIM PIN,3,3`），另外补了 `+CICCID`、`+CCSS?`、`+CLIP?`、`+CLIR?`、`+CMUT?`、`+CSCA?`、`+CSCB?`、`+CEREG?`；USSD、SIM 工具包、呼叫转移回 ERROR（它们走单行 / 数字方式，ERROR 安全）。
- **坑 4：网络类型显示「未知」**。注册状态（`+CREG/+CGREG/+CEREG`）最后一项接入技术要按 27.007 报 7（LTE），之前报 14 被映射成 UNKNOWN。
- **结果（安卓 14 实测）**：rild 不崩，SIM LOADED，语音 / 数据都 IN_SERVICE，运营商 csl.（45400、香港）。
- **安卓 13**：同一套直接通（模拟器安卓 13 的 vendor 里也有 libcuttlefish-ril-2.so）：SIM LOADED、IN_SERVICE、LTE、csl.，rild 不崩。板子用的是安卓 13 镜像，这条很重要。
- **安卓 15**：模拟器的 libcuttlefish_utils / libcuttlefish_fs 要的 libbase 函数（如 `android::base::Join<vector<string>,char>`）Redroid 15 的 vendor libbase 没有 → rild「dlopen failed: cannot locate symbol」反复重启。两份 libbase 各有对方没有的函数（fmt 库版本不同），**不能直接替换**（WiFi、传感器等都用它）。办法：`host/ril/private-libbase.py` 把模拟器那份改名 `libbas2.so`（名字等长，直接改 SONAME 字符串），只把缺函数的库的依赖改成它。实测通：SIM LOADED、IN_SERVICE、LTE，WiFi / 传感器正常，零崩溃。`build-wifi-image.sh` 对所有版本默认开新 rild（`PP_EMU_RIL=0` 可关）。

### 66. 摄像头：云上做不了（2026-11-16）
- 模拟器的摄像头服务（android.hardware.camera.provider.ranchu）通过同样的管道问模拟器要画面，但画面是模拟器直接写进它自己的显存（`frame ... offset=` 用 goldfish 显存的映射偏移），Redroid 的显存不是这种，出不了画面；它自带的「假摄像头」模式（ro.boot.qemu.legacy_fake_camera）只有一个后摄，也依赖 goldfish 显存。

### 67. 横竖屏切换（2026-11-16）

### 68. 挂载表里的容器痕迹：内核模块 pp_mnt（2026-11-16，代码完成，待宿主机加载实测）
- **现象**：App 能读 `/proc/self/mountinfo`、`/proc/mounts`，里面：根目录和 /apex/*、/etc 是 Docker overlay（`lowerdir=/var/lib/containerd/...`）；/data 及其各种 bind 带宿主机路径（`/opt/prism-phone/data/phones/<id>/data/...`，来源 /dev/sda1）；Docker 的 resolv.conf / hostname / hosts；管家伪造的 cpuinfo、midr_el1、version、build.prop、.empty（遮 vmallocinfo 等）；lxcfs 的 /proc/meminfo；小助手绑的伪终端（devpts 挂在 /dev/goldfish_pipe*）；mqueue、/dev/shm。
- **为什么用户态遮不住**：/proc/mounts 是链接到 /proc/self/mounts，各进程读各自的；bind 只能遮一个进程的（检查表里原来的结论）。
- **办法**：内核模块 `host/kmod/pp_mnt`：kretprobe 挂在内核输出每一行的 `show_mountinfo` / `show_vfsmnt` 上，读的进程属于登记过的云手机（按 **PID 命名空间** 认——安卓给每个 App 单开挂载命名空间，但不开 PID 命名空间）就改写刚输出的那一行：overlay → `253:0 ... ext4 /dev/block/dm-0 ro`；/data 那块盘 → 去掉宿主机前缀、`253:34 /dev/block/dm-34`；同一块盘挂到系统目录的伪造文件、别的宿主机盘、Docker 文件、lxcfs、mqueue、shm、多余 devpts → 删。`/dev/fuse`（/storage）照留，真机也是。只改读到的文字，不动真实挂载；宿主机和别的容器不受影响。
- 规则在 `rewrite.h`（纯 C，内核和用户态共用），`bash host/kmod/pp_mnt/test.sh` 用甲骨文上抄的真实挂载行测（目录 / 磁盘镜像两种 /data 都测）。管家开机读这台自己的 mountinfo 找 /data 的来源和路径，写 `/proc/pp_mnt`：`add <pid>|<root>|<来源>`（`agent/internal/phones/mounts.go`）。没模块就跳过。
- **编译**：甲骨文 6.17 内核 `bash host/build-kmod.sh --build-only pp_mnt` 通过（KPROBES/KRETPROBES 都开、三个函数在符号表里、没在 kprobe 黑名单）。**还没加载**：内核模块出错会让宿主机重启，等 24 小时稳定性测试结束再装上实测。板子要看厂商内核开没开 KRETPROBES（build-kmod 会自己检查，没开就跳过）。
- **剩下的**：statfs("/") 返回的文件系统类型仍是 overlay（和挂载表说的 ext4 不一致，要另挂 statfs）；设备号 st_dev 还是 0:53；/proc/self/mountstats 没改；Docker 的 proc / devpts 各多一份（被删会让 Android 那份的父 ID 对不上，先留着）。

### 76. 无线网卡名 pps<手机ID>（2026-11-17 全面体检发现；2026-11-17 复测确认暂时改不了）
- **现象**：手机里 /sys/class/ieee80211、/sys/class/net/wlan0/phy80211/name 是 ppsc3406ab039eb38（我们建 hwsim 网卡时起的名）。真机是 phy0。
- **本想的修法**：网卡搬进手机后 `iw phy#N set name phyK` 改成 phyN。
- **复测发现改不成**（甲骨文 6.17 内核）：`iw phy#N set name phy0/5/60/99` 全部 EINVAL（-22），`iw phy#N set name phyX`（非纯数字）却成功——**内核把 phy%d 这种名字留给自己自动编号用，不许手动改成 phyN**。所以原来那段改名循环（phy0…phy63）永远失败，名字一直留在 ppsXXXX。
- **正确的修法（需要在板子/测试机上多次开关机验证，暂缓）**：建 STA 网卡时**不给名字**，让内核自己起 phyN（新建的路由器命名空间里就这一块 wiphy，`iw phy` 读得回它的名字）；关机顺序是先停容器再 teardownWifi，这时 STA 网卡已回到宿主机命名空间、可能因重名被内核改名，所以删网卡要按 MAC 找、不能只按名字，否则会漏删、积累泄漏。这一改动动到 WiFi 的关机清理路径，盲改有网卡泄漏风险，留到有板子能反复开关机测时再做。
- **影响面小**：只有 /sys/class/net/wlan0/phy80211/name 这一个很偏的路径能看到，几乎没有检测库会读 wiphy 名字（常见的是 SSID/BSSID/MAC/扫描结果，这些都已处理）。其余 WiFi 相关都正常。

### 79. 多开的手机共用同一个值（2026-11-17 用户问「多开之后不能用一个数值」后查）

### 80. statfs("/") 还是 overlay 类型号——vfs_statfs 被内联了（2026-11-17 体检后复测发现）
- **现象**：pp_mnt 模块早就挂了 `vfs_statfs` 想把 statfs 返回的 overlay 类型号（0x794c7630）改成 ext4，但手机里 `stat -f /` 还是 overlay。模块是当前源码（srcversion 和现编的一致），不是旧的。
- **查法**：写了个只打印的诊断模块，挂 `vfs_statfs` 的返回看 f_type。结果所有调用返回的都是 **ef53（ext4）**，从来没有 overlay。
- **根因**：甲骨文 6.17 内核把 `vfs_statfs` **内联**进了系统调用路径（`vfs_statfs` 符号还在，但系统调用那层不走它），我们挂的 `vfs_statfs` 只抓到 overlay 内部对下层 ext4 的那次调用（返回本来就是 ext4），真正带 overlay 类型号的那层抓不到。
- **修法**（pp_mnt.c）：改挂 `do_statfs_native` / `do_statfs64`——内核把填好的 kstatfs 拷给用户前的最后一步，**入口**处 arg0 就是带 overlay 类型号的 kstatfs。用 kprobe 在进去前把 overlay 改成 ext4（只改登记过的手机）。诊断模块挂这两个函数入口确认 f_type=794c7630，对上。两个符号 best-effort 挂（哪个在挂哪个）。
- **实测**：重新编译加载后，三台 `stat -f /` 都返回 ext4；挂载表、DNS 不受影响。

### 81. 重载 pp_mnt 内核模块后登记全丢、不自愈（2026-11-17 修 #80 时发现）
- **现象**：重新编译、`modprobe -r pp_mnt; modprobe pp_mnt` 换上新模块后，`/proc/pp_mnt` 是 `phones 0`，三台手机的挂载表改写、statfs、端口隐藏全没了；重启管家也没补回来。
- **根因**：登记（写 /proc/pp_mnt）和端口防护只在 **Start（开机）** 路径里做；管家重启走的是 **ResumeRunning**，只补了 WiFi 和开机后设置，**没补登记**。平时管家重启登记在内核模块里还在，不用补；但一旦重载了模块（自动更新重编 pp_mnt 时就会），登记全丢，只能逐台重启手机才恢复。
- **修法**（resume.go）：ResumeRunning 的补做里加上 `applyMounts` + `guardLocalPorts`（都是幂等的，跟 Start 一样）。这样重载模块 + 重启管家就能自愈，不用逐台重启手机。

### 85.（更正，虚惊一场）uptime 其实已经归零——docker exec 看不进时间命名空间（2026-11-18）
- **一开始以为的差异项**：补漏扫描时 `docker exec pp-<id> cat /proc/uptime` 读到开机时长是宿主机的（113 天），三台还一样，以为是真差异项+标识重复。

### 87. 根目录残留空文件 /pp-init——喂数据子进程占着启动器（2026-11-18 用户「完整检测」发现，已修实测通过）
- **现象**：新机根目录留一个 0 字节的 `/pp-init`（App 列根目录看得到「pp-init」这个怪名字，差异项）。
- **根因**：`/pp-init` 是启动器（agent 二进制）bind mount 进来的，开机后 `removeTraces` 用 `umount -l` 卸它再 `rm`。但喂数据子进程 `vendor.sensord` 是 `startSensors` 从 `/proc/self/exe`（即 `/pp-init`）起的，整个开机期间一直把这个文件当自己的可执行映像占着 → lazy umount 永远落不了地（busy）→ `rm -f /pp-init` 报 EBUSY 删不掉，留个挂载点空文件。老机器上偶尔是干净的，纯看 rm 跟 lazy umount 谁先谁后，不稳。
- **修法**：`startSensors` 先把当前可执行文件复制进一块匿名内存文件（`memfd_create`，flags=0 不设 CLOEXEC 以便跨 exec 保留），从内存文件（`/proc/self/fd/N`）起 `vendor.sensord`，这样没人再占 `/pp-init` → `umount -l` 落地、`rm` 删得掉。`memfd_create` 系统调用号按架构放 `agent/memfd_linux_{arm64,amd64}.go`（arm64=279 / amd64=319，不引新依赖）；任何一步失败退回 `/proc/self/exe`，照常开机。
- **实测**（095a6ac，带谷歌 gapps 机 0e38587af6be）：`ls /pp-init` → No such file；`/proc/<vendor.sensord>/exe` → `/memfd: (deleted)`；开机正常、传感器/基带/触摸照常。
- **教训**：从 `/proc/self/exe` 起长期子进程会把这个 exe 文件钉死；要在开机后清掉它，就别让任何活进程拿它当可执行映像——复制进 memfd 再起。

### 90. /proc/uptime 空闲时间还是宿主机的——内核模块改写（2026-11-19，已部署实测）

- **现象**：`/proc/uptime` 第二个数（空闲时间）是宿主机累计的，几台手机一样、且远大于本机开机时长（宿主机开了 114 天、空闲 3800 万秒），App 一读就露馅。第一个数（开机时长）已由时间命名空间按每台调过，是对的（见 #85）。
- **改法**：pp_mnt 加一个 kretprobe 挂 `uptime_proc_show`，对登记过的手机把空闲改成 `本机开机时长 × 在线CPU数 × 0.98`（像刚开机不久、基本空闲的真机）。纯逻辑 `pp_rewrite_uptime` 在 rewrite.h，用户态单测覆盖（厘秒整数运算，不用浮点）。
- **验证要进对命名空间**：⚠️`docker exec cat /proc/uptime` 在引导命名空间、没进时间 ns，读到的还是宿主机开机时长（#85 同一个坑）。正确办法：`nsenter -t <容器init宿主机pid> -T -p -m -- /system/bin/cat /proc/uptime`（容器里没有 /bin/cat，要用 /system/bin）。实测 App 视角 `2361.36 9256.53`（2361.36×4×0.98=9256.53 ✓），修复前是 `2361.36 3800万+`。
- **安全加载流程（防失联）**：编到临时目录 → `rmmod` 旧 + `insmod` 新（**不覆盖** /lib/modules 里已装的旧模块，万一卡死重启自动加载回旧的）→ 确认宿主机 uptime 在涨、dmesg 无 oops → `systemctl restart prism-phone-agent` 重新登记（重载后登记清零，#81）→ App 视角验证 → `srcversion` 对上后才 `install` 到 /lib/modules 持久化。全程宿主机稳，无 panic/oops。panic_on_oops=0 也是一层保险。

### 91. /proc/modules 暴露宿主机和我们的内核模块——对 App 返回 EACCES（2026-11-19，已部署实测）

- **现象**：App（uid≥10000）读 `/proc/modules` 能看到宿主机所有模块 + 我们自己的 `pp_mnt`/`pp_uts`，直接暴露工具链。真机 SELinux 不让 App 读 proc_modules。
- **符号陷阱**：逐行函数 `m_show` 在这个内核里有 **2 个同名**（slabinfo 等也用），不能按名字挂 kretprobe（会挂错、搞坏别的 /proc 文件）。改挂**唯一的 `modules_open`**（`grep ' m_show' /proc/kallsyms` 先确认过）。
- **改法**：kretprobe 挂 `modules_open`。entry handler 判断「登记手机的 pidns + uid≥10000」才装返回钩子并存下 inode/file；return handler 把成功的 open 返回改成 `-EACCES`，并先 `seq_release` 释放 seq_open 分配的 seq_file（失败的 open 不会再调 release，再把 private_data 置空多一层保险）。root/system（uid<10000）照常能读（真机特权域也能读，保持一致）。
- **验证**：root 视角 `docker exec cat /proc/modules` 读到 133 个模块、含 pp_mnt（照常）；App 视角 `nsenter -t <pid> -T -p -m -S 10085 -G 10085 -- /system/bin/toybox cat /proc/modules` →「Permission denied」✓；回归 `/proc/uptime` 仍正确。宿主机稳、dmesg 无 oops / 泄漏。
- **没做的**：`/sys/module` 目录列举同样暴露模块名（过滤 sysfs 目录更复杂、更危险），留作单独一项。

### 92. statfs("/") 返回宿主机整块盘——overlay 改成系统分区大小（2026-11-19，已部署实测）

- **现象**：`/`、`/system`、`/vendor` 等 overlay 挂载点 statfs 返回宿主机整块盘（47973404×4KB≈196GB、Free 30075705、而且 fsid 都一样 190896e0f4b82b4d），几台手机必然一模一样，一看就是同一宿主机。`/data`（非 overlay）另算、不动它。
- **改法**：扩展已有的 statfs 钩子（`pp_statfs_pre`，挂 do_statfs_native/do_statfs64），对登记手机的 overlay 挂载点把块数改成 ~6GB、留 ~1.5% 空闲（基本占满，像只读系统分区）；`f_bsize` 不动、按它算 `f_blocks`。留一点空闲而不是 0，避免开机时有组件看到「0 空间」出岔。
- **验证**：新建 poco-x4-gt 安卓14 实测，开机正常（~15s；statfs 开机时也跑、不受影响）；App 视角 `df /` = `6.0G 5.9G 96M 99%`（不再是 196GB）。四项（含挂载搬迁 #89）在同一台新机上协同生效：根目录干净、`/proc/modules` 拒 App、`/proc/uptime` 正确。宿主机稳、dmesg 无异常。
- **没做的**：statfs 的 `f_fsid`（文件系统 ID）还是宿主机的、几台一样（App 很少读 statfs 的 fsid，先留着）；各 overlay 挂载点被改成同一个大小（真机各分区大小不同，但远比「196GB 宿主机盘」像手机）。

### 93. /pp-init 0字节空文件残留在根目录——搬进 /data（2026-11-19，已部署实测）

- **现象**：#87 本以为修好了（memfd 让喂数据进程不占启动器），但审计新机实测，开机几分钟后 `/pp-init` 还是 **0 字节空文件**残留在根目录——removeTraces 把它 umount 了但 `rm -f` 没删成（lazy umount 后挂载点仍 busy，或 memfd 偶尔回退到 /proc/self/exe=/pp-init 占着）。App 能 `ls /` 看到，是根目录差异项。
- **改法**：别再靠异步清理。直接把启动器挂载点从 `/pp-init` 搬进 `/data/.ppi`（和 .ppf/.ppl 一样，/data 权限 0771、App 列不了）。顾虑是 `/data` 可能 noexec、而启动器是被当容器入口**执行**的——但入口执行发生在**容器启动瞬间**，早于 Android 把 /data 重挂 noexec，所以能跑。
- **验证**：新建 poco-x4-gt 实测，start ok、开机 ~20s；根目录 `ls` 无 `/pp-init`（No such file）、无 .ppfake/.pplxcfs；`/data/.ppi` 在 /data 下（App 看不到）。
- **顺带发现**：check-tells 的蓝牙 #48 判断**误报**——prism.bt=1 且 rootcanal 在跑（ppbt 单元 active）时蓝牙是模拟可用的、`bluetooth_on=1` 是对的，不该报「没蓝牙硬件」。待修 check-tells。
- **这轮审计还剩的真差异项**：① `/sys/module` 列出 kvm/xen/virtio/vmw/hwsim + pp_mnt/pp_uts（19个，App 能列）——要挂 sysfs 目录读取、风险高，单独做；② SIM 卡没插（镜像旧 rild #65，要重建镜像）；③ 无线网卡名 ppsXXXX（#76 暂缓）。

### 94. /proc/stat CPU 累计时间是宿主机的——母机级相关性，按本机开机时长重算（2026-11-19，已部署实测）

- **现象**（横向对比 3 台发现）：`/proc/stat` 的 `cpu`/`cpuN` 行是宿主机从开机到现在的累计 tick（user/system/idle 几亿），**三台一模一样**、而且和各自开机时长完全不符（一台开机 1230 秒、一台 13 小时，cpu 累计却一样）。这是「一台母机跑多台」最直接的相关性——风控把几台的 /proc/stat 一比就知道同一台机器。对比之下 btime、boot_id、/proc/version 编译日期、uptime、statfs fsid 都已是每台一套（没问题）。
- **改法**：kretprobe 挂 `show_stat`（精确符号唯一，`awk '$3=="show_stat"'` 确认过；别被 show_state* 这些子串迷惑）。用文件里已对的 `btime` + `ktime_get_real_seconds()` 反推本机开机时长 up，把每个 cpu 行改成 `up×100×核数`（聚合）/ `up×100`（单核）的占用、基本空闲（idle 97%、system 1.5%、user 补余）；btime、intr/softirq（每条中断明细改起来易前后不一致）原样。**ctxt（上下文切换）、processes（fork 总数）这两个单数也是宿主机累计、几台一样，一并按开机时长重算**（ctxt≈up×1800、processes≈up×3+500，实测三台各不相同）。纯逻辑 `pp_rewrite_stat` 在 rewrite.h、用户态单测覆盖。`PP_LINE_MAX` 2048→4096 装下整文件。
- **验证**：加载后横向对比，三台 cpu idle 各为 1230/47767/47771 ×100×4×0.97，**各不相同、和开机时长精确对上**；回归 uptime/modules/statfs 都在；宿主机稳、dmesg 无异常、show_stat 挂上了。
- **意义**：这是「宿主机级相关性」的一类，和「每台身份不同」是两码事。换板子也会有（板子也是一台母机跑多台），属于该修的通用项，不是开发 VM 专属。排查思路：横向对比多台的同一个值，几台一样且和本机状态不符的，就是母机级泄漏。

### 95. 并发冷启动多台（尤其安卓15/谷歌）在 4 核开发机上会崩溃循环（2026-11-19 批量测试发现）

- **现象**：批量测试时，同时开 3 台（含安卓15 谷歌服务机型）→ 容器反复重建、能短暂 `boot_completed=1` 但稳不住，且删不干净（stop/delete 卡住）。
- **排查**：不是内存（free 显示 20G+ 可用）、不是 OOM（dmesg 无 oom-kill）、不是 docker 重启（`docker inspect RestartCount=0`，是容器被整体重建/Android 反复重启）。同一机型（poco-x4-gt a14）单独或宽松时能正常开机、挤在 3 台并发里就崩 → 指向**并发冷启动时 CPU 争抢**（4 核扛不住 3 个 Android + 谷歌服务同时冷启动，init/服务超时触发重启）。
- **结论**：大概率是开发机 4 核的资源上限（也是 `maxRunning=4` 的由来），不是代码 bug；真机 8 核板子应好很多。**待办**：① 用 `host/soak-test.sh` 在板子上压测确认；② 若要在 4 核机上多开，错峰开机（别 3 台同时冷启），或把并发冷启控制在 2 台。
- **批量撞库结论（同批，60 台建机读值）**：序列号/androidId/WiFi MAC/蓝牙 MAC/广告ID 各 60 个值全唯一、零撞库；蓝牙 OUI 大写格式正确。身份生成器规模下不撞车。
- **操作坑**：删数据多的手机很慢（30~60s/台），批量脚本要把 stop（秒级、释放 maxRunning 名额）和 delete（慢）分开；`docker exec` 要加 `timeout`，否则在重启中的容器上会卡死。

### 96. 板子直连 DC：Alpine(musl) 跑不了 DC 装的 glibc Node（2026-11-19，已解决上线）

- **背景**：要让魔云腾 Q1 板子**自己**挂到 Desktop Commander（DC），这样用户电脑关机也能连板子继续干活。用户在板子上跑官方 `curl .../install/remote-linux.sh | sh`。
- **现象（连环坑）**：
  1. `getaddrinfo EBUSY registry.npmjs.org`——其实是暂时性，板子**能**直连 npmjs（后面证实）；
  2. 真病根：DC 装脚本按 glibc 下了 **Node 24 的 glibc 版**到 `/usr/local/bin/node`（123MB），但板子是 **Alpine(musl)**，跑它先报 `libdl.so.2: cannot open shared object file`；
  3. 装 `gcompat`+`libc6-compat` 想救 glibc node → 过了 libdl，又卡 `fcntl64: symbol not found`（gcompat 对 Node 这种大二进制补不全）；
  4. 更糟：`gcompat/libc6-compat` 之类顺带让 `/lib/libstdc++.so.6` 变成 glibc 版，**连 Alpine 自带的 musl node 也崩**（`_ZSt21__glibcxx_assert_fail` / `__getauxval` / `__strftime_l` symbol not found）。
- **根因**：musl 系统不能跑 glibc 二进制；且**魔云腾固件在 `/lib` 预留了几个 glibc 库**（`/lib/libstdc++.so.6` 21MB、`libgcc_s.so.1`、`libdl.so.2`，Oct 19、无 apk 归属，是厂商为跑自己 glibc 程序放的），动态库搜索 `/lib` 在 `/usr/lib` 前面 → 把 musl 版 libstdc++ 盖住了。
- **解法（干净路线，别用 glibc node）**：
  1. 删掉 DC 装的 glibc node：`rm -f /usr/local/bin/node /usr/local/bin/npm /usr/local/bin/npx`；
  2. `apk del gcompat`（清兼容层）；
  3. 把厂商预留的 glibc 库挪开让 musl 版顶上：`mv /lib/libstdc++.so.6 /lib/libgcc_s.so.1 /root/glibc-stray-bak/`；
  4. `apk add --no-cache nodejs npm`（musl 原生 Node，Alpine 3.21 是 v22.23.5，符合 DC 要求的 ≥22.12）→ `node -v` 正常；
  5. `npm install -g @wonderwhy-er/desktop-commander@latest`（官方源，加 `fetch-retries 8`、`fetch-timeout 1200000` 扛国际线路抖动）→ 装到 `/usr/local/bin/desktop-commander`；
  6. `desktop-commander remote` → 打印设备码 URL，用户浏览器点授权配对；令牌存 `/root/.desktop-commander-device/device.json`（**重启不用再配对**）。
- **自启**：写 `/etc/init.d/desktop-commander-remote`（`supervisor="supervise-daemon"`、`respawn_max=0`、`export HOME=/root`、`after docker`、`need net`），`rc-update add ... default`。切换时用脱离 SSH 的 `setsid` 脚本杀旧进程+起服务（否则杀掉的正是自己这条命令通道）。
- **验证**：板子作为 DC 设备 `mytos-pro-q1` 上线，直接发命令可达（不过电脑）；supervise-daemon 托管（崩溃自动拉起）。
- **注意**：npmmirror/腾讯源对**极新的传递依赖**有同步延迟（卡在 `@supabase/auth-js@2.119.2` ETARGET）；官方源虽慢但有全量版本，配好重试就能装完。

### 97. /api/health 返回 503——自检只认 binderfs，把 Q1 静态 binder 误判（2026-11-19，已修未部署）

- **现象**：板子上管家服务 `started`、手机 `boot_completed=1`、一切正常，但 `GET /api/health` 返回 **503**（网页顶部会报自检未过）。
- **根因**：`agent/internal/selfcheck/selfcheck.go` 的 binder 检查只看 `/proc/filesystems` 里有没有 `binder`（binderfs）。Q1 内核**没 binderfs**（只有静态 `CONFIG_ANDROID_BINDER_DEVICES`，靠 mknod `/dev/binder`），这项必然失败 → 整个 `Report.OK=false` → 503。其余项（4K 页、PSI `/proc/pressure/memory` 在、Docker、硬盘）都过。
- **改法**：binder 检查改成 **binderfs 或 `/dev/binder` 存在任一即通过**（见分支 `fix/selfcheck-binder-static`）。重编管家部署后 health 变 200。
- **待办**：这次改动随下一次管家重编（和 GPU/去 dev-host 一起）一并上板，避免为一个 cosmetic 单独重编部署。

### Mali GPU 硬件现状（2026-11-19 核实，利好）

### 98. 多开 binder：docker bind 分配独立 binder；timens 在 Q1 内核上坏了（2026-11-20，实测3台并发通过）

- **目标**：一块板跑多台云手机。没 binderfs 的板子（Q1），多台 `--privileged` 容器默认都看到宿主同一个 `/dev/binder`（binder1）→ 抢占冲突 → zygote 崩溃循环。
- **方案（管家代码）**：Q1 固件已建好 36 个静态 binder 设备 `/dev/binder1..36`（minor=123−N）。管家给每台分一组（第 k 台 = binder(3k+1,3k+2,3k+3)），记在容器 `prism-phone.binder` 标签上；下次分配从「正在跑的容器」标签反推已用槽位（docker 是真相，**agent 重启也不撞**，实测重启后新机正确拿到 slot 2）。最多 12 台。
- **坑：binder 绑定不能放 pp-init 里**。先把绑定写在 pp-init（容器入口），结果发现板子根本没走 pp-init——因为板子带 `-no-timens`，而 `InitHelper` 只在 `!noTimens && timens.Supported()` 时才设，不设就不用 pp-init。
- **更深的坑：timens（CLONE_NEWTIME）在 Q1 内核 6.1.141 上会让安卓崩**。去掉 `-no-timens` 让 pp-init 跑起来后，容器 exit 1。隔离测试：`unshare(CLONE_NEWTIME)+exec` 后，exec 出来的进程建线程失败 `runtime: failed to create new OS thread (errno=22 EINVAL) newosproc`——安卓 zygote/system_server 建不了线程、起不来。Ashburn 内核上 timens 正常，这块板子内核不行（疑似 vendor 内核对 time namespace + clone 的支持有问题）。
- **最终方案**：binder 绑定改用 **docker bind**（管家在容器 spec 的 Binds 里加 `/dev/binderN:/dev/binder` 等），**不依赖 pp-init/timens**。容器 `/dev` 是独立 tmpfs（`tmpfs /dev ... size=65536k`）、binder1..36 节点都在里面，bind 只在本容器可见、不污染宿主。板子保持 `-no-timens`。实测 binder4/5/6 单台开机正常；3 台（poco-x4-gt / nothing-phone-2a / xiaomi-13t）并发各在 binder1/4/7 上 `boot_completed=1`，身份值（序列号/androidId）全唯一、零撞库。
- **板子正式配置**：`-gpu-family Mali-G610 -gpu-mode host -images 13=cnflysky/redroid-rk3588:lineage-20 -max-running 8 -mem-overcommit 2.5 -dev-host -no-wifi -no-sensors -no-host-guard -no-timens`。内存超卖 2.5（机型满内存累加会超 23G，实际每台只用 1~2G）。
- **遗留**：① timens 坏 → 开机时长用的是宿主机的（几台一样，母机级泄漏）。要么修 timens（改 fork 再 exec？），要么上 pp_mnt/pp_uts 内核模块的 uptime 钩子（待办，按板子内核 6.1.141 重编）。② `-no-sensors/-no-wifi/-no-host-guard` 还开着（lineage 镜像没我们的传感器/RIL 标签，等阶段8 定制镜像再逐个打开）。

### 99. 给 lineage Mali 镜像加传感器/RIL（定制镜像 + pp-init/timens 解耦）（2026-11-20，实测通过）

- **目标**：lineage-20 Mali 底子缺传感器和 RIL（`ro.radio.noril=yes`、sensors=0）。用 `host/build-wifi-image.sh cnflysky/redroid-rk3588:lineage-20 13` 从谷歌模拟器 android-33 扒 WiFi/传感器/RIL(电话) HAL，产出 `lineage-20-wifi`（标签 prism.sensors/ril/wifi/touch=1）。
- **坑1：手动 docker run 开不了机，gralloc 找不到**。`fixup-redroid-names.sh`（去 redroid 痕迹）把 `gralloc.redroid.so`/`hwcomposer.redroid.so` 按机型芯片名改成 `gralloc.mt6895.so` 等并删掉 redroid 那份，`gpu_config.sh` 让 `ro.hardware.gralloc` 跟随 `ro.hardware`。手动 run 没传 `androidboot.hardware=<SoC>`→`ro.hardware` 还是 lineage 硬编码的 `redroid`→找 `gralloc.redroid.so`（已删）失败→composer 打不开 framebuffer→SurfaceFlinger 卡住。**管家开机会重写 build.prop 把 `ro.hardware` 设成机型 SoC 名（mt6895），gralloc.mt6895.so 就找到了**——走管家正常，手动测试是假象。
- **坑2：传感器/RIL 靠 pp-init 喂，但板子 `-no-timens` 关了 pp-init**。原来 `InitHelper` 只在 `!noTimens && timens.Supported()` 时设，-no-timens→不挂 pp-init→传感器/RIL 喂不进。而 timens 在这板子内核又是坏的（踩坑 #98）。**解法：把 pp-init 和 timens 解耦**——只要喂传感器或 timens 其一需要就挂 pp-init；Timens 关时入口加 `--no-timens`，pp-init 走 `timens.Exec`（纯 exec 不建时间命名空间），照常喂传感器/RIL，只是开机时长不归零。
- **实测（走管家，poco-x4-gt / mt6895）**：入口 `pp-init --sensors={含 modem/thermal/电池/磁力} --no-timens 0 /init androidboot.hardware=mt6895`，`ro.hardware=mt6895`，开机 30s `boot_completed=1`。**传感器 6 个**（加速度/陀螺仪/磁力/距离/光线，MTK）、**telephony 框架激活**（识别到 modem、MediaTek modem 版本 MOLY.NR17...）、**Mali-G610** 渲染，Google Play 都在。
- **还差**：① SIM「插上」：modem 默认 `absent:true`，`simCountry/simOperator` 是 `mode:proxy`（跟代理的国家/运营商）——要配正式代理才有 SIM（需用户给代理）。② 拨号/短信 app：lineage 不带，要另跑 `host/build-apps-image.sh` 加 AOSP 拨号短信。③ 蓝牙：安卓13 模拟器蓝牙 HAL 走内核蓝牙、容器用不了（prism.bt=0）。
- **板子正式镜像**：`-images 13=cnflysky/redroid-rk3588:lineage-20-wifi`，去掉 `-no-sensors`（开传感器/RIL），`-no-timens` 保留（解耦后不影响喂数据）。镜像构建要在板子上（`apk add git gcc binutils unzip util-linux python3`，克隆仓库，临时目录改到 /mmc 别用小根分区）。

### 100. 复用魔云腾安卓镜像 + 安卓14/15 Mali 调研结论（2026-11-20）

- **用户想法**：与其在 lineage 上叠 HAL，不如直接复用魔云腾自己调好的安卓镜像（毕竟是为这板子调的）。合理，于是查到底。
- **魔云腾开源页**（github.com/opencecs）只有 5 个项目：pc-android-client、vnc-desktop-client、MYT-AI-server、**tebox**（Android GSI 运行基座）、web-client。其中 tebox 有 Mali，但是 **QEMU 架构**（HVF/KVM 跑 GSI），Mali 是「自研透传」（非可复用的 libmali 驱动），**不托管镜像、无 docker 支持** → 和我们 docker/redroid 架构不兼容，用不上。
- **魔云腾调好的 docker 安卓镜像**（tkyds/android、dobox）：① 在**私有 registry**（registry.cn-hangzhou.aliyuncs.com/whsyf/dobox），由其**云平台运行时动态下发 tag + 鉴权**拉取（正是收费/锁定机制）；② `/init` 有 AVB + 「not in v3 env」**DRM 锁**；③ 原来在 /mmc（docker data-root），**已被我清前任数据时 prune 删了**；④ 固件 rootfs（p8/p9 RAUC 双槽）里**不含**安卓镜像（运行时才拉）。→ **没法复用**。
- **安卓 14/15 的 Mali 镜像**：社区**没有**。RK3588 的 Mali redroid 只到安卓 13（cnflysky lineage-20）。14/15 要么大改 ROM（自己编 lineage-21/22 带 Mali vendor，大工程）、要么软件渲染（无 GPU 加速、慢）、要么魔云腾 Q14（上面说了拿不到）。注入 A13 的 Mali 用户态到 redroid 14/15 也不行（gralloc HAL 跨版本不兼容）。
- **结论**：这板子上「开源可复用、docker 原生、Mali 硬件加速」的安卓目前**只有安卓 13（lineage-20）**这一条路——也就是已做好的 `lineage-20-wifi`。14/15 带 Mali 属独立 ROM 工程，非本阶段能速成。

### 102. 正式网络打通：REDIRECT(NAT)模式替代 tproxy（2026-11-20，实测通，接 #101）

### 103. SIM 终于打通：基础镜像被剥了电话应用 + 全平台重签过签名墙（2026-11-20，实测通，接 #102/#65）

**现象**：rild↔基带模拟器(AT/9600)通、电话 HAL(IRadio AIDL slot1)已注册，但框架 `gsm.sim.state` 空、`dumpsys isub` 空、OUT_OF_SERVICE，`service check phone` = not found，logcat 里**一条 RILJ 都没有**。

**根因 1（缺拱心石）**：`cnflysky/redroid-rk3588:lineage-20` 把 AOSP 电话应用整个剥掉了（容器没真 modem，Redroid 默认不装）。`pm list packages` 里 telephony 相关只剩 `com.android.stk`，**没有 `com.android.phone`(TeleService) 和 `com.android.providers.telephony`(TelephonyProvider)**。没有 TeleService 就没有「phone」系统服务、不起 RILJ、框架根本不去问卡状态——下层 rild/HAL/基带配得再对也没人用。之前 #65/#101/#102 一直在修下层，其实缺的是这个上层应用。
- 解决：`host/build-telephony-image.sh` 从谷歌模拟器系统镜像(同版本纯 AOSP，和电话 HAL 配套)抠 TeleService + TelephonyProvider(+CarrierConfig)，产出 `<base>-tel`。

**根因 2（签名墙）**：`com.android.phone` 用 `sharedUserId="android.uid.phone"`，和 `com.android.stk` 同 UID，必须同密钥签。基础镜像是 **cnflysky 自己的私有平台密钥**签的（证书 subject `emailAddress=cnflysky@qq.com`，**不是公开 AOSP testkey**，GitHub 上也没公开这把私钥）。用 testkey 签的 TeleService 装上后，构造 `GsmCdmaPhone` 时要 `registerReceiver` for user -1，需要 `INTERACT_ACROSS_USERS_FULL`——这是**纯 `signature|installer` 级权限**（不是 privileged，`ro.control_privapp_permissions=disable` 也不给），只认平台签名(=framework-res，cnflysky 密钥)。于是 com.android.phone 崩溃循环（`SecurityException: ...requires INTERACT_ACROSS_USERS_FULL`）。
- 解决：容器没有 AVB/dm-verity，**签名是唯一门槛**。`host/build-resign-image.sh` 把镜像里**所有 apk（154 个）用 AOSP testkey 统一重签**（含 framework-res，即「android」包=平台签名），内部一致后平台签名=testkey，电话应用就拿到纯 signature 权限了。
- **保住 Google Play**：GMS/Play（GmsCore/Phonesky/GoogleServicesFramework/GoogleRestore）用自己的共享 UID `com.google.uid.shared`，**不和平台 UID 冲突**；重签会破坏 Google 的证书校验（`GoogleCertificatesRslt: not allowed`→Play 完整性/登录挂）。所以重签脚本**排除 Google 应用**(`GOOGLE_RE`)，保留它们的原厂 Google 签名。

**实测结果（镜像 `lineage-20-wifi-tel-resign`）**：`gsm.sim.state=LOADED`、运营商 **SmarTone**（香港，和代理出口一致）、`gsm.operator.numeric=45406`(MCC454/MNC06)、`mVoiceRegState=0(IN_SERVICE)`、`service check phone/isub/carrier_config` 全 found、SIM 卡 `CARDSTATE_PRESENT, USIM APPSTATE_READY, ICCID=898520625...`、IMEI/IMSI `service call iphonesubinfo` 能拉到、状态栏有蜂窝信号图标。SystemUI 开机有竞态崩几次但会恢复、稳定；GPU/gralloc/传感器/RIL HAL 都是 .so/二进制没动、不受重签影响。
- **构建链**：`lineage-20`(基础) → `-wifi`(WiFi/传感器/RIL HAL，build-wifi-image.sh) → `-wifi-tel`(加电话应用，build-telephony-image.sh) → `-wifi-tel-resign`(全平台重签，build-resign-image.sh)。
- **板子构建环境**：板子是 Alpine 3.21 aarch64，`apk add openjdk17-jre-headless zip`；apksigner.jar(跟架构无关)+ AOSP testkey 从谷歌源下；zipalign Alpine 没有、跳过（只影响 mmap 优化，非必需）。大文件全放 `/mmc`（eMMC 根分区只剩 ~200M，docker 数据根已在 /mmc）。

### 105. 安卓14 + Mali-G610 硬件加速：魔云腾 Mali 栈 graft 到官方 redroid14（2026-11-20，实测 boot+Mali 通）

**背景**：A13(lineage-20)能跑但太老。目标换新安卓(14) + Mali-G610 硬件渲染。魔云腾 dobox 安卓镜像整体有 DRM 锁死不能用，但它的 **Mali 用户态驱动**（和咱板子内核的 bifrost KMD 同版本 g18p0-01eac0）能单独抠出来配干净官方 redroid。详见 `host/mali/README.md`、`docs/进度记录.md` 第 7 节。

**做法（`host/build-mali-image.sh`）**：从 dobox 的 `super.img` 用纯 Python `lpextract.py` 抠 vendor 逻辑分区（LP 动态分区，无 lpunpack 也能解；注意 LINEAR extent type=0、ZERO=1，别搞反），`debugfs rdump` 导出，复制 Mali 图形栈核心件（`libGLES_mali.so` UMD + gralloc `allocator/mapper@4.0-impl-bifrost` + allocator@4.0-service），graft 进 redroid 的 `/vendor`，`gpu_config.sh` 设 `ro.hardware.egl=mali` 走硬件 EGL。

**踩的坑**：
- **sphal 命名空间看不到依赖**：vendor 进程的 linker namespace(sphal)只认 `/vendor/lib64` + VNDK-SP/LLNDK 白名单。Mali 栈依赖的 `libdmabufheap.so`、`libgralloctypes.so`、HAL 接口库、`android.hardware.graphics.common/allocator-V*-ndk` 等不在白名单 → `library "xxx" not found in namespace sphal` → `host/mali/graft-deps.py` 算 NEEDED 闭包，把 sphal 看不到的非 VNDK-SP 库全补进 `/vendor/lib64`。
- **必须 64 位**：`arm.graphics-V3-ndk` 这种，copydeps 可能挑到 `odm/lib` 的 32 位 stub → `graft-deps.py` 用 ELFCLASS64 检查，只取 64 位版。
- **VINTF 缺 mapper 声明**：`Gralloc4: mapper 4.x is not supported` → `host/mali/manifest_mali_a14.xml` 补 `mapper@4.0` passthrough + `allocator@4.0` hwbinder 声明。
- **gpu_config 别用 mesa**：管家默认传 `-gpu-mode host`，但 host 走 mesa，在这板子配不上 Mali 的 EGLConfig → SurfaceFlinger `no suitable EGLConfig found` 崩。改成**只要有 `/dev/mali0` 就走 mali 硬件直通**（host/mali/auto 都走），guest 才软件。
- A14 vs A15：A14 gralloc 用 **HIDL** `allocator@4.0-service`；A15 用 **AIDL** `allocator-V1-service`。A15 另有 `CpuPowerStatsCollector` 在容器里崩 system_server（和 Mali 无关，纯官方 redroid15 也崩）→ A15 待 aconfigd 适配，先做 A14。

**实测**：`boot_completed=1`、`dumpsys SurfaceFlinger` → `GLES: ARM, Mali-G610, OpenGL ES 3.2 v1.g18p0-01eac0`、14 个传感器、拨号短信、RILJ 注册。产出 `prism-redroid-mali:14`，再叠 wifi/tel/resign/apps 成完整镜像（和 A13 同一套 `build-*.sh`）。

### 107. 带谷歌(全量多架构)镜像必须纯 64 位化，否则 system_server 崩在 bootCompleted（2026-11-20，实测通）

**现象**：普通 A14 Mali 镜像（基于 `redroid:14.0.0_64only`）开机顺，但**带谷歌** A14 Mali 镜像（基于 #106 的 `_mindthegapps` 全量底子）开机卡住 → 框架重启循环，`sys.boot_completed` 永远不置 1。

**诊断两层**：
1. logcat crash buffer：`app_process32` 在 `/system/lib/libEGL.so android::Loader::open` **abort** → 32 位 `zygote_secondary` 预加载 EGL 时找 32 位 Mali 驱动，而**魔云腾硬件 Mali 只有 64 位**（`/vendor/lib64/egl/libGLES_mali.so` 有，`/vendor/lib/egl/` 里根本没有 mali；RK3588 这套栈就是纯 64 位）→ 崩溃循环。
2. 光设 `ro.zygote=zygote64`（关掉 32 位 zygote）**还不够**：system_server 在 `ActivityManagerService.finishBooting → ZygoteProcess.bootCompleted → attemptConnectionToSecondaryZygote` 去连那个已不存在的 32 位 zygote socket → `IOException: No such file or directory` → **`FATAL EXCEPTION IN SYSTEM PROCESS: android.display`** → system_server 死 → 重启循环。关键：system_server 认不认 32 位看的是 **`ro.product.cpu.abilist32`**，全量底子里还列着 `armeabi-v7a,armeabi`。

**根因**：带 Mali（纯 64 位硬件栈）的镜像**必须是纯 64 位**；全量多架构底子残留 32 位 ABI/zygote 配置和它冲突。

**修（`host/build-mali-image.sh` 第 [7.5/8] 步，已固化）**：graft Mali 后，把底子**所有分区 build.prop**（system/vendor/odm/product/system_ext）里：`ro.*.cpu.abilist=arm64-v8a`、`ro.*.cpu.abilist32=`（清空）、`ro.zygote=zygote64`——和纯 64 位底子 `redroid:14.0.0_64only` 完全一致。
- 管家生成每台机的 build.prop 是**照抄镜像的**再改机型属性（`/mmc/pp-data/phones/<id>/buildprop/N.prop` bind-mount 到各 `build.prop`），所以**改镜像即可，无须动管家**。
- 对纯 64 位底子（本来就没 32 位 ABI）这步 `grep` 不中 → **幂等空操作**，不影响普通镜像链。
- 坑中坑：容器里 `/vendor/build.prop` 是管家 bind-mount 的（`sed -i` 报 `Device or resource busy`，rename 盖不过去）→ 只能在**镜像层**改（redroid 镜像没 `/bin/sh`，`docker build RUN` 用不了 → 用 `COPY` 补丁层导出-改-COPY回）。

**实测（`prism-redroid-mali:14-gms-wifi-tel-resign-apps`，管家建带谷歌 A14 手机）**：`boot_completed=1`（50s）、`GLES: ARM, Mali-G610`、`com.google.android.gms` 进程在跑 + `com.android.vending`(Play) + gsf、拨号短信桌面、RILJ 注册、`init.svc.zygote=running` 且**无 zygote_secondary**、无 system 崩溃。SIM 走 direct-dev 代理无国家→ABSENT（预期，真代理 HK/US/CN 会 LOADED，机制同 A13）。

### 108. 安卓15/16 开机崩在 CpuPowerStatsCollector，清空 timeInState.o 解决（2026-11-20，实测通）

**现象**：纯官方 `redroid:15.0.0_64only`（不装 Mali）在这板子上也开不了机，`sys.boot_completed` 永远不置 1，`system_server` 每 ~4 秒崩一次重启循环。A13/A14 没事。

**崩溃点**：`FATAL EXCEPTION IN SYSTEM PROCESS: batterystats-handler` → `java.lang.IndexOutOfBoundsException: Array is too short, size=1, scalingStep=1` at `CpuPowerStatsCollector$KernelCpuStatsReader.nativeReadCpuStats`。读 AOSP android-15 源码：`mCpuTimeByScalingStep = new long[mCpuScalingPolicies.getScalingStepCount()]`（Java 按 sysfs `/sys/devices/system/cpu/cpufreq/policyN/scaling_available_frequencies` 算 CPU 频点数给数组定大小），native 按**内核 eBPF `time_in_state` map** 的频点数往数组里写 → RK3588 vendor 内核的 eBPF 频点数和容器 sysfs 对不上 → 越界抛异常。A15 新增这个 collector，A13/14 没有。

**为什么 aconfig 那条路走不通（排除过的弯路）**：gating 这个 collector 的 flag 是 `com.android.server.power.optimization/streamlined_battery_stats`。解析 `/system/etc/aconfig_flags.pb` 发现它是 **state=ENABLED, permission=READ_ONLY**——只读 flag 的值编译期焊死进 framework.jar 的生成代码，**运行时根本不读 aconfig storage**。所以 `aflags`/aconfig storage override 对它无效；容器里 aconfigd 没初始化 storage（`/metadata/aconfig/{maps,boot}` 空，因为各分区 `/etc/aconfig/` 源 storage 文件 redroid 没生成）是**红鲱鱼**，和这个崩溃无关。

**修（固化进 `host/build-mali-image.sh` 第 [7.5/8] 步，SDK≥35 自动触发）**：`CpuPowerStatsCollector.collectStats()` 里有 `if (!mIsPerUidTimeInStateSupported) return null;`，而 `mIsPerUidTimeInStateSupported = KernelCpuStatsReader.isSupportedFeature()` → native `nativeIsSupportedFeature()` 就是 `startTrackingUidTimes() && getTotalCpuFreqTimes().has_value()`，即**查 eBPF time_in_state map 在不在**。→ 把 `/system/etc/bpf/timeInState.o` 清成 0 字节：bpfloader 跳过它（不报错、不中断开机）→ 那套 `map_timeInState_*` 不建 → `isSupportedFeature()=false` → collector 走 AOSP 自带的降级路径跳过，不崩。副作用仅 per-app CPU 耗电统计略降级，云测机无所谓。**实测**纯 redroid15 + 清空 timeInState.o → `boot_completed=1`、system_server 稳定不重启、FATAL=0。

### 109. 安卓15/16 把 Mali graft 到 redroid 的本质差异：Android 15 删掉了 VNDK（2026-11-20，实测通）

**现象**：A14 那套 Mali graft（`build-mali-image.sh`）搬到 redroid15，libGLES_mali 加载不了：`vndksupport: Could not load /vendor/lib64/egl/libGLES_mali.so from sphal namespace: dlopen failed: library "libunwindstack.so" not found`。补了 libunwindstack 又缺 liblzma，级联。

**根因**：**Android 15 把 VNDK（含 VNDK-SP）整个删了**，redroid15 没有 `/apex/com.android.vndk*`。A14 时代 `libc++/libz/libbase/libcutils/libutils/libhidlbase/libunwindstack/liblzma/libziparchive/libtinyxml2/libcrypto…` 这些是 **VNDK-SP**，vendor/sphal 命名空间能从 system 看到；A15 的 sphal（`/linkerconfig/ld.config.txt` 的 `namespace.sphal`）只链 `/vendor`、`/odm` + **LLNDK** 白名单（`/etc/llndk.libraries.txt`：libEGL/libc/libm/liblog/libvulkan/libselinux/libnativewindow… 就这些），其余 VNDK-SP 老库**全看不到** → Mali 栈 dlopen 级联 "not found in namespace sphal"。

**修（`host/mali/graft-deps.py`）**：`CORE`（不复制进 vendor、假设 sphal 可见的白名单）原来按 A14 的 VNDK-SP 列，太宽。缩到**只剩真正的 LLNDK + bionic/linker**（照抄 `llndk.libraries.txt` + `ld.config.txt` 的 `namespace.sphal.link.default.shared_libs`），其余依赖闭包里的库全部从库池复制进 `/vendor/lib64`（redroid15 补齐 21 个，比 A14 的 12 个多出那些 VNDK-SP 老库）。对 A14 也安全：那些库在 Q14 vendor 库池里就有、同版本，复制=原样回填。

**Mali 驱动版本的坑**：Q15/Q16 dobox 的 Mali UMD 是 **g29p0**，但板子内核 KMD 是 **g18p0**（bifrost_kbase g18p0-01eac0，UK1.18），**版本对不上配不了**（g29p0 用户态要 g29p0 内核）。所以 A15/16 的 Mali **不能用 Q15/Q16 自己的栈**，要复用**能匹配 g18p0 内核的 Q14 HIDL@4.0 Mali 栈**。实测 A15 仍接受 HIDL `allocator@4.0`+`mapper@4.0`（`init.svc.vendor.gralloc-4-0=running`），不必换 Q15 的 AIDL `allocator-V1`。

**实测（`prism-redroid-mali:15-base` = redroid15 + Q14 g18p0 Mali + timeInState neuter）**：`boot_completed=1`、`GLES: ARM, Mali-G610, OpenGL ES 3.2 v1.g18p0-01eac0`、system_server/surfaceflinger 稳定、FATAL=0、gralloc-4-0 注册成功、安卓版本 15(SDK35)。`build-mali-image.sh` 现在同一条命令（BASE 换成 redroid15/16）就能产 A15/A16 的 Mali 底子。

### 110. 安卓15 完整镜像必须跳过「全平台重签」，否则 fs-verity 崩在 framework 加载（2026-11-20，实测通）

**现象**：A15 Mali 底子（`prism-redroid-mali:15-base`）独立开机好好的，但叠完整链（`-wifi-tel-resign-apps`）、管家建手机后开机崩：`PackageManager: Failed to load frameworks package` → `VerityUtils: Failed to measure fs-verity, errno 25 (ENOTTY): /system/framework/framework-res.apk` → `Failed to collect certificates ... using APK Signature Scheme v4` → `system_server` 重启循环。

**根因**：罪魁是**重签**那一步（`build-resign-image.sh`，踩坑 #103）。它存在的理由是 A13 底子 `cnflysky/redroid-rk3588:lineage-20` 用的是 cnflysky 自己的**私有**平台密钥，补进的 AOSP testkey 电话应用拿不到 signature 权限，必须整镜像重签成 testkey。**但官方 redroid 14/15/16 的 framework-res.apk 本来就是 AOSP 公开 testkey 签的**（`apksigner verify` 看到 `EMAILADDRESS=android@android.com, CN=Android`），补进的 testkey 应用**本来就匹配平台签名，根本不需要重签**。而重签改了 framework-res.apk 的内容、却留下它原来的 `.idsig`（APK Signature Scheme v4 签名文件），两者失配：A15 的 `PackageManager` 一见 apk 带 `.idsig` 就走 v4 校验、要对 apk 做 `FS_IOC_MEASURE_VERITY` ioctl，容器的 /system 文件系统不支持 fs-verity（errno 25 ENOTTY）→ v4 失败 → framework 包加载失败 → 崩。

**为什么 A14 重签没事、A15 就崩**：A14 的 `.idsig` 也是失配的（A14 也重签了），但 A14 的 `PackageManager` 对 v4/fs-verity 宽容（失败能回退 v2/v3）；A15 收紧了，带 `.idsig` 就强制走 v4 fs-verity，失败即致命。

**修（`host/build-board-image.sh`）**：`VER>=15` 跳过 resign 步骤（链变成 `base→wifi→tel→apps`）。不重签 framework-res.apk → 它原厂的 `.idsig` 仍然有效、v4 校验过得去 → 不崩；补进的电话/拨号/短信（AOSP testkey）本就和官方 redroid 的平台签名一致，SIM/电话权限照样拿到。A13（私有密钥）仍需重签；A14 维持原链不动（已验证在用，避免扰动生产 `-images 14=`）。

**实测（`prism-redroid-mali:15-wifi-tel-apps`，管家建 A15 手机）**：`boot_completed=1`（20s）、`GLES: ARM, Mali-G610`、framework 崩 0、拨号/短信/电话、RILJ 注册、17 传感器、FATAL=0、稳定。SIM 走 direct-dev 无国家→OUT_OF_SERVICE（预期，真代理会 LOADED，机制同 A13/A14）。

### 附：构建脚本的临时文件要放 /mmc（板子根分区只有 3.5G）

`build-{apps,resign,telephony}-image.sh` 的 `sign()` 用 `mktemp`（默认落 `/tmp`=板子 eMMC 根分区，只有 3.5G）。A15 构建时根分区被填满 → `cp: No space left on device` → build-apps 失败。对策：跑这些脚本时 `export TMPDIR=/mmc/pp-build/tmp`（mktemp 认 `$TMPDIR`），大文件全走 NVMe（/mmc，384G）。另 build-apps 的 x86 aapt2 回退路径硬编码 `/opt/prism-phone/...`（也在根分区），本机 aapt2 读不了 A15 资源时会尝试下 qemu+build-tools，桌面布局那步是 best-effort，失败自动跳过（和 A14 一样用默认 Launcher3 布局），不影响开机。

## #111 风扇 PWM 极性反了（+ 服务没进仓库）→ 满载过热、盒子假死掉线（2026-11-20）

**现象**：做 A15 大镜像构建时盒子（魔云腾 Q1 / RK3588）负载飙高后 DC 连续十几分钟无响应、最后彻底掉线（心跳停更，过热保护关机）。用户发现**正面风扇没转**。

**根因（真凶是极性，不是没自启）**：`pwmchip1/pwm0` 的**默认极性是 `inversed`（反的）**，而 `fan-control.sh` 没把它扳正。于是脚本"温度越高 duty 越大"配上反极性 = **duty 越大风扇越慢、duty=0 反而全速** → 该猛转时（高温高 duty）风扇恰恰停了 → 满载必过热。验证：手动 `echo 40000 > duty_cycle`（满 duty）用户听不到风扇；`echo normal > polarity` 扳正后同样满 duty，风扇立刻呼呼全速转。
- 次因：板子上确实有个老 `/etc/init.d/fan-control` 服务（跑同一脚本），但**没进仓库**（README 一键部署清单里也没有），且本次开机发现它处于 `crashed`。所以刷机/重装不会恢复它，等于也没有可靠的风扇自启。

**修（三处）**：
1. `fan-control.sh` 开头 **`echo normal > $PWM/polarity`** 强制扳正极性（放在 enable 之前），"越热越快"才真生效。
2. 新增 OpenRC 服务 `host/board/etc/init.d/prism-phone-fan`（`command_background=yes`，`depend` 里 **`before docker prism-phone-agent`**——先转风扇再上重负载），进仓库；README 一键部署补 `rc-update add prism-phone-fan default`（顺带补漏掉的 `prism-phone-oled`）。
3. 删掉板子上重复的老 `fan-control` 服务（`rc-update del` + 删文件），避免两个守护抢同一 pwmchip1。

**教训**：① 用户态 PWM 控风扇，**先确认极性**（`cat polarity`，默认可能是 `inversed`），脚本里显式 `echo normal > polarity` 别靠默认。② 安全关键的板子级守护写完必须同时落 init.d + rc-update **并进仓库**；刷机后 `rc-update show default` 逐项对一遍。③ 满载前确认 `polarity=normal` 且升温时 `duty_cycle` 跟着变大、手摸风扇在转。

**应急**：扳极性 + 手动起风扇 `echo normal > /sys/class/pwm/pwmchip1/pwm0/polarity; setsid /usr/local/bin/fan-control.sh >/var/log/pp-fan.log 2>&1 &`；已过热假死只能断电散热后再上电。

### 112. 安卓16 把 eBPF 对象扩展名从 .o 改成 .bpf，timeInState neuter 要清两个（2026-11-20，实测通）

**现象**：A15 那套 Mali graft + timeInState neuter 搬到 redroid16，`prism-redroid-mali:16` 独立开机：Mali-G610 加载成功、版本 16，但 `sys.boot_completed` 不置 1，`FATAL EXCEPTION IN SYSTEM PROCESS: batterystats-handler`——和 A15 一模一样的 `CpuPowerStatsCollector` 崩溃。奇怪的是 `build-mali-image.sh` 的 neuter（踩坑 #108）明明按 SDK≥35 清空了 `/system/etc/bpf/timeInState.o`（实测它确实是 0 字节），但容器里 `/sys/fs/bpf/` 还是建了 18 个 `map_timeInState_*`。

**根因**：**Android 16 把 `/system/etc/bpf/` 下 eBPF 对象的扩展名从 `.o` 改成了 `.bpf`**。A16 镜像里是 `timeInState.bpf`（20560 字节），`timeInState.o` 只是个残留/空壳。bpfloader 在 A16 加载的是 `.bpf`，所以只清 `.o` 根本没碰到真正的那个 → map 照建、collector 照崩。`find / -name '*imeInState*.o'` 看到的 `.o` 是幌子，真家伙是 `.bpf`。

**修（`host/build-mali-image.sh` 第 [7.5/8] 步）**：SDK≥35 时把 `timeInState.o` **和** `timeInState.bpf` 都 COPY 成 0 字节。对 A15（只有 `.o`）多出个空的 `.bpf`，A15 的 bpfloader 不认它、无害；对 A16 清掉真正加载的那个。两版一条命令通用。

**实测（`prism-redroid-mali:16` 清 `.bpf` 后）**：`/sys/fs/bpf` 的 timeInState map 数 = 0、`boot_completed=1`（10s）、`GLES: ARM, Mali-G610, OpenGL ES 3.2 v1.g18p0-01eac0`、安卓版本 16(SDK36)。A16 其余（graft-deps 删 VNDK 补 21 依赖、纯 64 位化、build-board VER≥15 跳 resign、emu `arm64-v8a-36_r02`）全部复用 A15 那套、无需额外改动。
